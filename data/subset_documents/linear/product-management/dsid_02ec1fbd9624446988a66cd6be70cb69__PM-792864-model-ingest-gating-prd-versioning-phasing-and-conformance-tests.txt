Model ingress gating PRD: versioning phases, conformance tests, and scoped rollback triggers

Summary: This PRD defines a gated onboarding flow for new open-model submissions to the Redwood model catalog that standardizes versioning phases, conformance tests to validate runtime compatibility, and explicit rollback triggers. Goal: reduce runtime regressions and emergency rollbacks by catching incompatibilities early in the intake pipeline and giving clear decision criteria to intake reviewers.

Problem statement: We continue to see intermittent runtime incompatibilities and performance regressions from community weights that were ingested with minimal runtime metadata. Current onboarding practices are inconsistent across reviewers, and some models reach hosted/Dedicated without adequate conformance verification, causing costly hotfixes.

Scope: covers the product requirements and acceptance criteria for the intake UI/metadata contract, automated conformance test suite, staged rollout phases (trial, monitored, GA), documented versioning/semver expectations, and the set of runtime metrics and alert thresholds that will trigger automatic temporary unlisting or rollback. Does NOT include the underlying kernel/runtime changes or GPU scheduling policies (those are engineering scope).

Success metrics: fewer catalog-related runtime incidents (target 60% reduction in catalog regressions in first quarter after rollout), mean time to detect incompatibility < 30 minutes for new ingest, and >90% of new ingest items pass automated conformance checks without manual rework.
Initial draft proposed only a metadata contract. After stakeholder feedback (runtime, research, console), scope expanded to include: (1) automated conformance test harness running against canary runtime; (2) three-phase rollout policy for catalog entries (trial/monitored/ga); (3) temporary-unlist flow with explicit rollback triggers. These additions were approved by PM+Eng leads on 2026-03-03.
Metadata contract: every ingest must include stable model_id, weight provenance URL, architecture string, tokenizer spec, max_sequence, supported_attention_types, kv_cache_behavior, memory_profile_reference, quant_modes_supported, and recommended_variant_aliases.
Versioning phases: intake -> trial (restricted traffic) -> monitored (expanded traffic) -> GA (full listing). Each phase requires a passing conformance report and defined metrics windows.
Conformance suite: automated E2E checks executed in an isolated canary runtime that validate inference correctness (sample prompt suite), latency & p95 SLO, memory/KV cache sanity under short & long context, and deterministic tokenizer mapping tests.
Rollout controls: a per-entry policy with thresholds for latency, error rate, and quality regressions that automatically halt progression or trigger temporary unlisting.
Operational artifacts: reviewer UI with pass/fail conformance report, links to failing traces/PRs, and one-click temporary-unlist with audit note required.
Metadata contract enforced by ingest API: missing required fields cause rejection with actionable error messages.
Conformance harness runnable in CI and as a pre-ingest canary job; results stored and surfaced to the reviewer UI with failure categorization (compat|performance|tokenizer|memory).
Three-phase rollout implemented: trial (0.5-1% traffic), monitored (5-10%), GA (default), with ability to abort or rollback at each phase via console action.
Automated rollback triggers defined: p95 latency increase >50% vs baseline for 5m, error rate >1% sustained for 10m, or quality eval A/B score drop >5 points; each trigger produces an incident and marks the entry as 'temporary-unlisted'.
Reviewer workflow created: PM/Research/Runtime must approve trial->monitored transitions; approvals are auditable.
Documentation and on-call runbook published in Confluence with playbooks for common failure modes.
Use 'version-lock' terminology (immutable catalog artifact) rather than 'pin' to align with release engineering vocabulary.
Conformance suite will include a lightweight public prompt bank (50 prompts) maintained by Research for initial quality checks and a private extended bank for customer-sensitive scenarios.
Temporary-unlist is reversible only after a new passing conformance run and a mitigation plan entry in ticketing system.

Risk: False positives from conformance tests could block good models. Mitigation: allow reviewer override with documented justification and metered manual approvals; collect FP rate stats for 30d and refine tests.
Risk: Added latency to onboarding pipeline increases time-to-publish. Mitigation: parallelize conformance runs and provide fast 'trial-only' lightweight checks to enable quicker trial publishing.
Risk: Increased operational surface area for on-call. Mitigation: automate alert routing, provide runbook, and limit trial traffic to reduce blast radius.
Engineering will expose an ingest-validation endpoint that returns a structured text report (status and failure reasons). Conformance harness will be parameterizable: run with short-context and long-context profiles. Reviewer UI will include a timeline showing metrics for 1h/6h/24h windows during trial. Research will maintain the public prompt bank as a versioned artifact in the model-catalog repo.
Happy path: ingest with full metadata -> conformance pass -> trial -> monitored -> GA. Verify reviewer approvals and audit logs.
Failure path: ingest missing tokenizer mapping -> ingest API rejects with error code and suggested remediation steps.
Rollback path: during trial, artificial load causes p95 spike; system auto-marks temporary-unlist and creates incident; confirm rollback and reingest after fix.
