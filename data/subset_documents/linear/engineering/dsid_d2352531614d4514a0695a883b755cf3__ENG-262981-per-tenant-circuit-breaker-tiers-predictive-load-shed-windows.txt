Per-tenant circuit-breaker tiers with predictive load-shed windows and phased rollback safety

Background: Dedicated and Private control planes occasionally face sudden tenant spikes during upgrades or regional failovers. Current reactive circuit-breaker behaviour opens abruptly and relies on static thresholds which either cause noisy tripping or late intervention that lets SLOs degrade. We need a per-tenant, tiered circuit-breaker system that proactively creates short predictive load-shed windows and supports phased rollback-safe behaviour during control-plane upgrades and multi-region failover events.

Goals:
- Provide per-tenant, configurable circuit-breaker tiers (green/yellow/red) with clear escalation semantics.
- Predictive load-shed windows: use short-term forecasting (5m lookahead) and admission-queue signals to open soft windows preemptively before SLO breach probability > 60%.
- Phased rollback-safety hooks: ensure that any CB-triggered shedding is reversible via a staged unwind that respects KV cache warmup and request affinity.
- Integrate CB events with the Console and runbooks so SRE/SEs can triage and institute manual overrides quickly.

Design notes / Decisions so far:
- Tiering: green = best-effort (no shedding), yellow = graceful degradation (limit concurrency/seq-len, return 429 with Retry-After), red = emergency shed (reject non-critical routes, allow high-value reserved-capacity tenants).
- Signals used: p99 latency, error rate, admission_queue_length, GPU_utilization, token_per_second, short-term anomaly score from traffic forecaster.
- Predictive model: lightweight EWMA + Holt-Winters variant running in control plane (not per-host) to keep latency and memory footprint low. Will be exposed as a single probability value per tenant -> feed into decision engine.
- Safety: circuit openings always start in a 'soft' mode for 30s where degraded responses are flagged but prefetched KV cache is allowed; if violation persists 2x window, promote to hard open.
- Upgrade interplay: upgrades should annotate draining nodes with tenant CB sticky hints so newly scheduled capacity doesn't immediately re-accept shed requests until warmup thresholds met.
- Fallback: Automatic backfill policy to route shed requests to compatible model variants or a regional standby if tenant allows.

Open questions / tradeoffs:
1) How aggressive should the predictive thresholds be? Initial target probability = 60% (tunable).
2) Who owns per-tenant tier assignments? Default mapping based on committed capacity, with overrides via Console (product work).
3) Interaction with Dedicated autoscaler: ensure CB does not hide true load and starve autoscaling signals. We're adding a separate scaling metric based on 95th tail of observed accepted requests.

Acceptance criteria (see list below): implementation must be feature-flagged and deployed behind canary policy; no SLO regressions on a set of 3 synthetic tenant workloads; dashboards and runbook created, and a postmortem simulation demonstrates controlled shedding under a 2x spike test.
Per-tenant CB tiers implemented and configurable via control-plane API and Console UI (green/yellow/red)
