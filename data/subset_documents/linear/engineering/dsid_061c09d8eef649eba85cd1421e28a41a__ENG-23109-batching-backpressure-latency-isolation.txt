Graceful batching backpressure and latency isolation for continuous prefill/decode

Motivation: Our continuous-batching pipeline currently prioritizes throughput, but under certain request mixes (short chat turns mixed with long-prefills) we see tail latency spikes and unfair slowdown of latency-sensitive routes. This ticket implements a graceful backpressure and latency isolation layer in admission control plus lightweight batch shaping hints so kernel selection and attention optimizations remain performant at the tail. The goal is to reduce 99.9th token latency for latency-sensitive routes by 35-50% without losing >10% aggregate throughput on heavy mixed workloads.

Scope: admission scoring, soft priority queues, prefill-aware shape hints emitted to the batcher, and a small runtime admission policy that can trigger compact kernels or decode-only fast paths. This work should be orthogonal to autoscaling and focused on per-GPU runtime scheduling and request admission.

Non-goals: changing global QoS for Dedicated customers, implementing persistent per-customer reservations, or adding billing changes. Those are follow-ups managed under Reserved Capacity roadmap.
1) End-to-end e2e test shows 99.9th token latency improvement >= 35% for latency-tagged route under mixed synthetic workload (short chat probe + long prefill).
2) P99 and P99.9 for throughput-only benchmarks degrade by <10% vs baseline.
3) No regressions in unit tests; integration tests for kernel fallback exercised.
4) Feature flag gated and can be toggled per-cluster; rollout doc merged.
5) Github PR with runtime + admission unit tests merged and performance dashboard linked.
High-level design: add an admission scorer computed at request enqueue time: score = alpha * latency_sensitivity + beta * prefill_length_norm + gamma * cache_hit_priority. Requests with score above threshold go to a fast-path soft-queue with small max batch size and strict latency timer; lower scored requests enter throughput queue where the batcher shapes larger batches. The scoring is additive and configurable by route.

Kernel interaction: fast-path queues trigger compact-kernel selection (fewer fused attention kernels, minimal KV routing) to reduce per-token latency; throughput queues prefer wide-kernels and aggressive batching. We will expose a 'batch_hint' metadata field from admission to the kernel selector runtime that can be used to prefer FP16-fused kernels for latency peers and quantized kernels for throughput peers.

Attention optimization: for latency-tagged requests we will enable early-attention pruning (heuristic based on prefix similarity) to reduce attention compute for long prefills when safe. This is implemented as a costed decision that falls back if model logits change above a threshold.

Trade-offs considered:
- Setting too-small fast-path batch sizes reduces throughput; choose conservative defaults and tune via canary.
- Kernel switching adds overhead; amortize by caching kernel choices per (model, seq_len_bucket, batch_hint).
- Attention pruning can change outputs; limited to routes with regression guards and eval prompt sets.

Configuration: all knobs behind feature flag runtime.batching.latency_isolation; defaults off in Prod, enabled in canary clusters.
