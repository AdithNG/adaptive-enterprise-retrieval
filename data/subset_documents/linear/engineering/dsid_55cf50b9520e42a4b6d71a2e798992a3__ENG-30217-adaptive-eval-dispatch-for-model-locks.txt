Adaptive eval dispatch for model-version locks with tenant-aware prioritization

Background: When a model version is locked/pinned in the catalog or by a tenant we need an automated, cost-aware evaluation run to detect regressions before traffic is routed. Current ad-hoc workflows produce uneven coverage and delayed detection for lower-traffic tenants. Goal: Implement an adaptive eval dispatching service that consumes pin/upgrade events, prioritizes targets by tenant impact and traffic, deduplicates simultaneous events, and schedules a staged evaluation (smoke -> sampled synthetic -> full-fidelity) with quota controls and audit logging.
Introduce an eval-dispatch microservice in the control plane. Workflow: 1) Pin/upgrade event emitted from catalog/tenant API -> 2) dispatch service normalizes event and calculates priority score (traffic-weight, SLA tier, catalog-critical flag) -> 3) select eval profile (smoke, sampled, full) using tenant policy and historical variance -> 4) schedule runs to eval-runner fleet with rate limits and cost budget -> 5) aggregate results and write to catalog/tenant change log; trigger rollback/alert webhooks if thresholds exceeded. Key features: idempotent event handling, per-tenant budget tokens, adaptive sampling that favors low-traffic tenants with synthetic trace replay, and backpressure to avoid overload during large catalog changes.
Pin/upgrade events for both catalog and tenant-locked models reliably create dispatch records (>=99.5% success)
Dispatch service deduplicates repeated pin events within 10 minutes for same version/tenant
Smoke eval completes within SLO (90th percentile < 30s) and returns pass/fail
Adaptive sampling picks representative prompt sets for low-traffic tenants and completes within configured budget
Triggering path produces audit log entries with event id, priority, and eval outcome visible in console change history
When regression threshold is breached, an automated alert and tenant-scoped rollback recommendation are produced

We can either run full-fidelity evals for all pinned upgrades (high cost, best sensitivity) or use adaptive sampling (lower cost, risk of missing rare regressions). Chosen approach: staged evaluations with option to force full runs for high-SLA tenants. This balances cost and coverage. Another trade-off: complexity of tenant budgeting vs. simple global throttle; we prefer per-tenant tokens to avoid noisy tenants consuming budget.
Start with conservative default thresholds for alerting to reduce false positives
