Runaway Tenant Isolation & Reservation Healing Protocol for Dedicated Clusters

Summary: During a recent dedicated-cluster capacity incident, a single tenant's workload entered a sustained high-CPU/high-kv-cache churn pattern that exhausted shared burst tokens and caused cascading tail-latency spikes for colocated tenants. This ticket defines a mitigation and long-term healing protocol we will implement: (1) fast detection of runaway tenants using new telemetry windows, (2) soft isolation fences (pacing + temporary reservation carve-outs), (3) automated reservation "healing" (gradual right-sizing back to baseline), and (4) observability + runbook updates.

Goals and acceptance criteria:
- Detect noisy/runaway behavior within 30s of onset with <5% false positive rate in historical backtest.
- Automatically impose a soft pace (per-tenant token bucket) within 60s for confirmed runaway tenants and re-balance reservation allocations so critical tenants keep SLOs.
- Implement a reservation healing workflow that reduces human ops to advisory steps: automated shrink on overload + automated grow once stable for 10m, with human approval for >2x changes.
- Add dashboards and alerts (PagerDuty runbook) so SREs can validate incidents and cancel automated actions if needed.

Scope of work (implementation plan):
1) Telemetry and detection (owner: Priya Rao)
   - Add a 3-window detector: 30s, 5m, 30m for per-tenant CPU, GPU utilization, token consumption, and KV cache churn.
   - New derived metric: tenant_runaway_score (0-100) computed from normalized z-scores of the three windows.
   - Backtest detector on last 6 months of Dedicated telemetry; tune thresholds to meet FP/FN targets. Query examples and initial PromQL stored in Confluence: https://confluence.redwood.ai/dedicated/runaway-detector

2) Soft isolation (owner: Liam O'Connor)
   - Implement per-tenant pacing middleware that enforces a token bucket at the routing layer (configurable per-reservation).
   - Add ability to temporarily move N% reservation from offender into a transient quarantine pool and reassign reservation to high-priority tenants.
   - Safety: soft isolation must never reduce a reservation below 10% of committed baseline without manual approval.

3) Reservation healing (owner: Marco Alvarez)
   - Healing state machine: detected_overload -> soft_isolated -> monitor_stable -> gradual_restore (5 steps) -> healed.
   - If healing does not reach stable after 30m, escalate to SRE and optionally trigger eviction playbook.

4) Telemetry + observability (owner: Zoe Chen)
   - New dashboards per-cluster and per-tenant: runaway_score, reservation_delta, burst_tokens, tail_p95_p99_latency.
   - Alert: runaway_score > 70 for 2 consecutive 30s windows -> PagerDuty P1 with link to runbook and automated isolate action summary.

5) Runbook & customer comms (owner: Maya Patel)
   - Update Dedicated incident runbook with automated healing steps, cancellation paths, and FAQ for customers.
   - Draft templated customer notification for incidents where reservation healing changed effective capacity.

Trade-offs considered:
- Aggressiveness vs false positives: We bias towards conservative automatic actions (soft pacing + 10% floor) to avoid customer surprise; more aggressive automatic evictions require manual approval.
- Complexity: we add a 3-window detector to reduce oscillation and better separate short spikes from sustained runaway. This increases compute for telemetry but reduces manual toil.
- Rollout speed vs correctness: initial rollout will run detector in "observe-only" mode for 7 days and then enable soft isolation in canary clusters before full enablement.
