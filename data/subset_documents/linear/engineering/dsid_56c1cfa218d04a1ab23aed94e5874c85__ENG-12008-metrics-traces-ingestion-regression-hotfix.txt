Telemetry ingestion regression: missing metrics and span linking broke console during incident

Multiple customers across Hosted, Dedicated and Private reported that during the Feb 14th incident their Console dashboards showed blank charts and traces could not be linked from logs to spans. Paging alerts originated from missing per-route SLO metrics and a sudden drop in request_agg ingestion. This ticket tracks the hotfix, root cause analysis, and follow-ups to prevent recurrence. Scope: telemetry ingestion pipeline (metric aggregator + trace linker), Console dashboard rendering, and alerting rules that depend on the missing series.
1) Deploy the metric name normalization feature (feature flag ff-metrics-normalization) in a lab environment with high cardinality traffic.
2) Run synthetic traffic that contains new label sets (tenant_id + custom_route).
3) Observe aggregator logs: series dropped due to UnrecognizedMetricName error.
4) In Console, open the per-route latency dashboard and traces view — charts are empty and trace links return 404 or 'span not found'.
A recent change to metric name normalization introduced a strict validation step that rejected metric series with unexpected label keys when cardinality exceeded buffer thresholds. The aggregator returned a non-200 internal status that dropped the series instead of backfilling or tagging as 'unknown'. In parallel, the trace linker relied on a mapping table populated by the same ingestion path; because the series failed, trace->request linking failed and Console could not render related spans. The regression surfaced only under bursty/high-cardinality traffic patterns present in Dedicated and some Hosted customer workloads.
1) Reverted the strict-validation path and introduced a safe fallback that accepts unknown label keys as 'unnormalized'.
2) Added a short-lived in-memory queue to prevent drops during bursts (preserves order and retries to the normalization worker).
3) Restored graceful error handling so the aggregator emits 'ingestion.accepted=false' with metadata instead of dropping.
4) Fixed trace linker to fall back to raw request IDs when mapping table entries are missing, avoiding 404s in Console.
5) Added unit + fuzz tests for high-cardinality label sets and an e2e synthetic test that exercises ingestion + linking.
1) Deploy hotfix to staging and run the synthetic high-cardinality job for 6 hours.
2) Canary rollout to 5% of Hosted traffic + one Dedicated customer node for 2 hours.
3) Monitor ingestion metrics (ingestion.accepted ratio), Console chart render rates, and trace linking success.
4) If stable, escalate to 50% then full rollout over 8 hours.
5) Communicate to on-call and affected customers at each step.
