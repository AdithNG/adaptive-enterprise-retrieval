Title: Usage Insights: reconciliation suite vs billing totals + CI drift gate

Summary
We’ve had a few early beta reports that “console totals don’t match invoice” (see SUP-24811) and a recurring internal concern that aggregation lag + rounding will cause subtle drift. This PR adds a reconciliation suite that compares Usage Insights rollups (route/model aggregates) against billing totals (metering hooks → invoice preview) within a defined tolerance, and wires it into CI + a nightly scheduled run with alert hooks.

Key goals
- Catch drift early (instrumentation regressions, bucketing/alias issues, timezone boundary mistakes, rounding deltas).
- Define and document a tolerance policy that is strict enough to catch real issues but robust to expected effects (late events, FX rounding, minimum billable units).
- Provide a runbook-friendly output: workspace/project, day/hour, route/model slices that contribute most to drift.

What’s included
1) Reconciliation job + report format
- New job: services/telemetry/reconciliation/usage_insights_vs_billing
- Compares totals for a given workspace_id + time range across:
  - usage_insights.route_model_agg (the dataset powering console breakdown tables)
  - billing.usage_totals (billing hook rollups used for invoice preview)
- Outputs both:
  - a single “gate” metric per workspace/time window (pass/fail)
  - a ranked list of top contributing slices (route/model/region/deployment_mode where present)

2) Tolerance policy (documented + implemented)
We gate on both absolute and relative drift, and we avoid evaluating windows likely to be incomplete.
- Windows evaluated:
  - Hourly buckets for last 24 hours (excluding most recent 2 hours)
  - Daily buckets for last 7 days (excluding current day)
- Late-event buffer:
  - Ignore the most recent 2 hours entirely to avoid normal ingestion lag.
  - For daily checks, only evaluate days older than 26 hours.
- Tolerance thresholds:
  - Absolute drift allowed: max($2.00, 2000 tokens worth of cost at the workspace’s effective blended rate) per evaluated window
  - Relative drift allowed: <= 0.50% per evaluated window
  - Gate fails if BOTH absolute and relative drift exceed thresholds (prevents false positives on small totals)
- Currency handling:
  - Compare in USD using billing’s canonical conversion for the period.
  - Usage insights cost uses the same price book snapshot key as billing (price_book_version) to avoid rate drift.
- Rounding:
  - Compare on unrounded micros (int64) where available; rounding only applied in the human report.

Tolerance helper (illustrative snippet):

function isDriftAcceptable({ expectedMicros, actualMicros }) {
  const driftMicros = Math.abs(actualMicros - expectedMicros);
  const rel = expectedMicros === 0 ? (actualMicros === 0 ? 0 : 1) : driftMicros / expectedMicros;
  const absOk = driftMicros <= ABS_TOLERANCE_MICROS;
  const relOk = rel <= 0.005;
  return absOk || relOk; // fail only if BOTH are violated
}

3) CI + scheduled runs
- Adds a Buildkite step (non-blocking in PRs, blocking in main nightly):
  - PR builds: runs reconciliation unit tests + one small integration fixture
  - Nightly: runs full reconciliation across allowlisted beta workspaces with paging
- New pipeline: .buildkite/pipelines/usage-insights-reconciliation.yml
- Artifacts:
  - Uploads a CSV and JSON summary for each run
  - Posts a summary comment to #eng-platform on failures with a link to artifacts

4) Alert hooks + runbook pointers
- On gate failure, the nightly job:
  - Emits metric: usage_insights.reconciliation.drift_exceeded{workspace_id, window_type}
  - Logs structured payload with top slices and suspected causes
  - Posts to Slack: #usage-insights-alerts
  - Creates a lightweight incident event (non-page) unless drift persists 2 consecutive runs, then page the on-call (aligns with SRE feedback from earlier threads)

5) Guardrails to avoid noisy failures
- Workspace allowlist for beta reconciliation (config in services/telemetry/reconciliation/config/beta_allowlist.yml)
- Suppression for known exceptions:
  - If billing is missing a price_book_version for the period (rare), mark “skipped” not “failed”
  - If insights freshness lag > threshold (uses existing freshness metadata), mark “skipped”

Why this approach
- We compare at the same conceptual level as customers: “what billing says you owe” vs “what console says you spent”.
- We still include drill-down slices to make debugging actionable (route/model/region).
- Late-event handling is explicit and conservative; we don’t want to treat expected lag as correctness drift.

Rollout notes

- If the nightly job is noisy, we can widen the late-event buffer or adjust absolute tolerance; prefer changing absolute tolerance first.
- No change to customer-visible console behavior.
