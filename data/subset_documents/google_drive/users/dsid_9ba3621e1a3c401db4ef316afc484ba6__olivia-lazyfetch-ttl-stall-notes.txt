Lazy-fetch TTL / partial GCS fetch — scratchpad

Goal: capture breadcrumbs for the intermittent model-load failures where the lazy-fetcher stalls or returns truncated shards when fetching weights from GCS signed URLs.

Symptoms observed:
- In-host logs: repeated failures during model init while streaming shards.
  - Loader prints: "EOFError: Ran out of bytes while reading tensor" or "tar: Unexpected EOF"
  - HTTP fetch logs show intermittent HTTP 503 or connection reset after about ~30–90s of a long-running ranged GET.
  - Example message: "fetcher: download aborted (status=503) url=gs://models-prod/abc/shard-0004.data range=0-1048575"
- Client-level: retry logic sometimes gets a partial file stored to cache, subsequent attempts reuse partial file and fail checksum.
- Repro rate: ~1.2% of loads over last 30d; spikes during heavy rollout windows.

Commands / quick repro attempts tried locally:
1) Basic gsutil fetchs (single threaded)
- gsutil cp gs://models-prod/abc/shard-0004.data ./shard-0004.data 
  -> usually succeeds, hash matches, suggests underlying object valid on GCS.

2) Simulate ranged streaming (emulate lazy-fetch behavior)
- curl -f -H "Range: bytes=0-1048575" -o part.bin "$(signed-url)"
  -> sometimes returns 206 partial content; sometimes HTTP/1.1 503 Service Unavailable mid-transfer.

3) Using wget/aria2 to see resumable behavior:
- aria2c -x 4 -s 4 -c "$(signed-url)" -o shard-0004.data
  -> aria2 resumes ok on most failures; reproduces issue only when multiple parallel requests hit the same underlying object (points to GCS loadbalancer / signed URL TTL?).

4) Compare metadata & checksum via gsutil:
- gsutil stat gs://models-prod/abc/shard-0004.data
  - md5/hcrc/size all consistent between objects that fail and those that don't.

5) Validate manifest vs on-disk objects:
- cat weights_manifest.json (v2 style) contains byte ranges and offsets. Verified that manifest offsets are sane and sum to total file size.

Observed error snippets copied from logs:
- "ERROR loader: safetensors.InvalidHeaderError: unexpected magic bytes"
- "ERROR fetcher: http error 503 for url=... shard-0006.data range=52428800-62914559 attempt=2"
- "WARN model-init: checksum mismatch expected=2b7e... got=3f1a... file=/tmp/cache/shard-0006.data.partial"
- "Traceback (most recent call last):
  File "/app/loader.py", line 248, in _map_shard
    tensor = torch.load(streamed_file)
  File "torch/serialization.py", line 783, in load
    raise EOFError('EOF while reading file')
EOFError: EOF while reading file"

Hypotheses (ranked):
1) Signed URL TTL / GCS backend transient 503s trigger partial downloads which our fetcher treats as complete (race between close + rename).
   - We saw partial files with .partial suffix being atomically renamed into cache when last chunk came back, but if last chunk is missing the rename still happened in our older code path.
2) Multithreaded parallel Range requests against the same object get rebalanced to different GCS servers; one server returns truncated/timeout responses for long ranges.
3) Manifest vs object format mismatch: some older bundles uploaded with "weights_manifest_v1" (different offset ordering) are being interpreted by the v2 loader leading to bad range requests.
4) Disk pressure + mmap fallback: when ephemeral disk fills we fall back to streaming, but the fallback path has weaker retry semantics.

What we've tried and results:
- Change: make fetcher write to unique temp file (uuid) and validate size+sha256 before rename.
  - Result: reduced incidents but not eliminated. We still saw a case where the final size matched but content was corrupt (implies truncation followed by zero-padding? or server returned erroneous content-length).

- Change: force single-threaded ranged fetch for shards > 1GB (no parallel ranges)
  - Result: lowered repro rate during rollouts, but still occasional 503 mid-range.

- Change: enable resumable downloads using Google resumable upload/download protocol (python google-cloud-storage Transport).
  - Result: more resilient to connection drops, but doesn't change server-side 503 for long-lived ranges.

- Add extra verification step after download: compute gsutil hash locally and compare to manifest-stored checksum. Faulty ones flagged and retried from scratch (delete partial + retry).
  - Result: prevented bad file from being used; increased cold-start latency by ~0.2s on average.

- Temporary workaround: when loader detects EOF/InvalidHeader, attempt full object re-download via gsutil cp and then re-run. This unblocked some incidents quickly in prod.

Notes from correlating logs with rollout schedule:
- Incidents align with two events: (a) >3 parallel model loads for same bundle from multiple hosts and (b) large Cloud Build activity that modifies object ACLs (not sure if related).

Ideas to investigate / next steps:
1) Reproduce deterministically: create a small local MinIO cluster and a proxy that randomly aborts mid-range to emulate GCS 503; run our lazy-fetcher against it and observe rename vs validation logic.
2) Add server-side metrics: log content-length headers and last-byte-range-received from HTTP responses. Add a debug flag that keeps the .partial file (don't rename) and dump first/last 256 bytes to S3 for offline inspection.
3) Harden fetcher: require full-hash validation before rename. If hash matches manifest, atomically rename. If content-length reported by server != bytes received, fail and retry.
4) Investigate signed URL generation: ensure TTL covers expected long downloads (especially for ranged downloads that may need multiple attempts). Potentially extend TTL for large shard downloads.
5) Ask infra/cloud to check GCS SLA/incidents during spike windows and verify load balancer behavior for large ranged GETs.
6) Update manifest & uploader: standardize on weights_manifest_v2 format and add uploader-side test that verifies the object can be fully ranged-read by a simple script immediately after upload.
7) Add a small e2e test in PRs that uploads a test shard and runs 100 parallel ranged reads to catch LB-related truncation.

Short-term runbook (for on-call):
- If model load fails with EOF/InvalidHeader: 
  1) Check /var/log/fetcher*.log for "partial" files and their sizes.
  2) Run: gsutil stat gs://<bundle>/shard-XXXX.data && gsutil hash -m gs://<bundle>/shard-XXXX.data
  3) If gsutil reports object intact, run: gsutil cp gs://... /tmp/shard && compute sha256; compare to manifest. Replace cache with gsutil-copied file.
  4) If gsutil stat fails intermittently, escalate to cloud infra (include window and request-id) and enable fetcher DEBUG logs.

- Are there any proxies (envoy/nginx) in front of our instance that could be truncating long-lived responses? Look at egress iptables/sidecars.
