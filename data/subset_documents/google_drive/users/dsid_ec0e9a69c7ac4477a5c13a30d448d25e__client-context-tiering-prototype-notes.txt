Client context tiering — prototype notes

PURPOSE
Quick personal prototype notes for a client-side context tiering approach: keep small, privacy-sensitive pieces local (hot), push anonymized/embedded summaries to server (warm), and optionally archive raw long-form to customer-controlled storage (cold). Goal: reduce upstream token cost and latency while preserving enough fidelity for quality responses and retaining user privacy controls.

Problem space / motivation
- Many LLM calls include long, mostly-static context (chat history, docs). Uploading full context every request is wasteful.
- Some context is privacy-sensitive (PII) and should never leave client devices in raw form.
- We need heuristics to decide what to 1) keep local, 2) send as embeddings, 3) send raw text, or 4) skip.
- Backend should accept partial context with signals about fidelity and provenance so it can degrade gracefully (e.g., return a response based on just warm+hot).

Core concepts (v0)
- Tiers: HOT, WARM, COLD
  - HOT: recent messages + ephemeral UI state; stays on-device, may be sent as short deltas only when necessary
  - WARM: semantically important context (long-term notes, user prefs) converted to embeddings/metadata and uploaded; retrievable and searchable server-side
  - COLD: large attachments / raw documents; optionally stored in customer S3/GCS and referenced by opaque pointer; not sent on every request

- Fidelity flag (per-item): raw | redact | embed | pointer
- Confidence score: heuristics/ML that mark items as likely-relevant to current intent (0.0-1.0)
- Freshness / TTL: per-item TTL to force re-embedding or eviction

Client-side heuristics (rough)
- Token cost threshold X: if full context would push token cost over X, prefer offload to WARM embeddings or COLD pointer
- Recentness multiplier: messages < 2 min ago are HOT by default
- PII detection: if item tagged contains PII -> prefer redact or local-only (HOT with redact) unless user explicitly allows
- Semantic importance: use light-weight on-device classifier (or cheap embed similarity against intent) to bump to WARM

API shapes (sketches)
- POST /v1/session/context/push
  body: {
    "session_id": "s-abc123",
    "items": [
      {"id":"m1","fidelity":"raw","tier":"hot","text":"Where is my receipt?","ts":"2025-03-06T12:01:00Z"},
      {"id":"note-42","fidelity":"embed","tier":"warm","embedding_id":"e-77f","summary":"expense: travel 2024"}
    ],
    "intended_instruction": "summarize recent receipts for expense report"
  }
  server response: acknowledges accepted items, returns missing embedding-key instructions or a partial-accept header if some items were rejected for policy

- POST /v1/session/context/query
  body: {
    "session_id": "s-abc123",
    "include_tiers": ["hot","warm"],
    "context_budget_tokens": 1024
  }
  response: {
    "assembled_context": ["hot: m1 (raw)", "warm: note-42 (embedding ref)"],
    "cost_estimate_tokens": 840,
    "provenance": ["hot-local-only","warm-embedding"],
    "warnings": ["embedding-e-77f stale: older than TTL"]
  }

Notes on server behavior
- Server should be able to accept embedding references (embedding_id) and fetch stored vectors for retrieval in the similarity search/augment step.
- If embeddings are missing or stale, server should request a re-upload via a short code or return a single negative ack and provide the reasons.
- Model prompt builders should be aware of provenance and might apply different weighting to HOT vs WARM context (e.g., HOT has higher recency weight).

Privacy model
- By default, HOT raw pieces are not uploaded unless user opts in. Client UI must surface when raw context leaves device.
- WARM embeddings are irreversible by design; still store minimal metadata (hash of id, optional user-supplied tag).
- Provide per-item revocation: delete embedding_id -> server removes vector and any derived indexes (confirm via audit log id).

Eviction / compaction
- Periodic compaction job on client: group many small messages into a synthetic summary item (embed that), mark originals as COLD+pointer.
- Warm TTLs staggered by importance score (higher importance => longer TTL).

Open questions / TODOs
- How do we compute a reliable on-device "importance" cheaply? Tiny distil model? heuristic rules? hybrid?
- Interaction with Redwood routing/fallback: if hot-only, but a dedicated model variant expects warm embeddings, we should fallback to smaller model or ask client for more context. Which UX?
- Billing: how to surface billing when client chooses to send raw vs embedding? show estimate preflight? charge for embedded retrieval?
- Concurrency: client devices may push multiple embedding updates for same logical item. Need canonicalization keys and server-side delta-apply semantics.
