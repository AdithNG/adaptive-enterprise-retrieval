Disconnected client handoff and typed sink proposal

Context and motivation:

We frequently see client-side disruptions (mobile sleep, flaky networks, browser tab backgrounding) causing partial or abandoned streaming responses. Today the Hosted API streaming surface is optimistic: it sends incremental frames but assumes the client remains connected to receive them. This makes tool-calls and structured sinks brittle: partial tool invocations can be left in limbo, and downstream consumers must reconcile incomplete frames.

Goal (high level):
- Provide a pragmatic, low-friction protocol and SDK ergonomics so clients can gracefully handoff/resume in-progress streaming calls and tool invocations.
- Ensure typed/structured sinks (JSON blocks, action frames) reach a consistent final state even across disconnects.
- Minimize server-side state while preserving developer ergonomics and predictable billing semantics.

Success metrics (initial):
- Reduce customer-reported failures for streaming tool-based integrations by 60% within 3 months of rollout.
- < 2% increase in median per-request latency from handshake overhead on cold sessions.
- Resume success rate >= 95% for reconnects within 5 minutes for resumable sessions (best-effort).

Non-goals:
- This PRD does NOT propose long-lived server pins for >24h resume (that belongs to session persistence feature).
- Not addressing cross-region failover in this iteration.

Design principles / constraints:
- Keep server-side retention minimal (short-lived resume tokens, compact deltas).
- Favor deterministic, idempotent tool invocation semantics: tool calls must be retry-safe or wrapped in a transaction token.
- Backwards-compatible: existing simple streaming clients should continue to work without changes.
- SDKs should provide ergonomic defaults (auto-resume attempts, simple opt-in for persistence).

Key concepts introduced:
1) Handoff token: opaque short-lived token (TTL default 10m) issued during a streaming call. Allows a reconnecting client to request missing frames/deltas and to reattach to the in-progress evaluation.
2) Typed sink checkpoints: server-side compact snapshots of the structured output (e.g., last-valid JSON action block) stored as deltas. Checkpoints are coarse-grained and bounded (max 4 checkpoints per request, default cadence every 2s or at structured-sink boundaries).
3) Tool-call receipts: each tool invocation emitted by the model is accompanied by a lightweight receipt (tool_id, call_id, idempotency_key, status). Receipts are persisted until the handoff TTL expires. If a reconnect occurs the client can query receipts to deduplicate or resume pending calls.

API-level proposal (surface sketches):
- StartStreaming (existing): returns stream with incremental frames AND an optional handoff_token when the server detects eligible conditions (session long-running, complex tool calls, or explicit client request).
- ResumeStreaming(handoff_token, last_frame_id): server responds with missing frames, latest typed-sink checkpoint, and current receipts.
- QueryReceipts(call_id | idempotency_key): idempotency-safe API to ask about tool invocation status.
- SinkCommit(call_id, final_payload): explicit commit for structured sinks when client wants to assert finality (optional; useful for serverless consumers).

Behavioral guarantees (best-effort semantics):
- Within TTL: resume attempts will deliver frames deterministically in order since the last_frame_id provided, up to checkpoint boundaries.
- After TTL expiry: server will return a clear terminal marker; clients must fall back to reissue requests.
- Tool-call idempotency: if a receipt shows a tool-call completed successfully, any reissued call with same idempotency_key is treated as a no-op by the server/router. Tool vendors must honor the idempotency_key contract (we provide primitives to help).

SDK ergonomics (JS / mobile):
- Default behavior: short-lived automatic resume attempts (exponential backoff up to TTL), transparent to developer.
- Opt-in persistent mode: developer can request a longer TTL (customer account policy) for important flows; requires opt-in in the SDK and billing implication warning.
- Simple API surface: StreamingClient.attach() returns an object with events: onFrame, onCheckpoint, onToolReceipt, onResumeAttempt, onTerminal.
- High-level helpers: auto-merge typed JSON frames into a single object until a SinkCommit or terminal marker arrives; expose a raw stream for power users.

Tool developer guidance (server-side / adapter contract):
- Treat receipts as authoritative for dedup. Provide a small adapter layer that translates receipt semantics into backend semantics (e.g., dedupe vs idempotent-update).
- For actions that are not naturally idempotent (external writes, side-effects) require explicit idempotency_key and, if unavailable, mark the call as non-resumable in the receipt (notify client).

Observability & billing implications:
- Emit resume metrics: resume_attempts, resume_success_rate, avg_resume_latency, percent_frames_delivered_via_resume.
- Bill resumed-delivered tokens to the original request owner with a resume label; show breakouts in Console.
- Track lost-resume events (client attempted resume after TTL) and link to customer support flow.

Security / privacy notes:
- Handoff tokens are bearer tokens and must be scoped to the request+project; TTLs short by default.
- For Private/Dedicated customers we honor their retention policy and can offer configurable TTL through account-level configuration (requires explicit compliance review).

Compatibility matrix / migration story:
- Existing streaming clients: continue to function. They will not receive handoff_token unless server-side heuristics trigger it or they set a new flag start_streaming({enable_handoff: true}).
- SDK-enabled clients: immediate benefit: resume attempts and auto-merge of structured frames.
- Third-party tool adapters: must adopt receipt contract to get idempotency guarantees. Provide a shim library to help adapt common tool backends (HTTP webhooks, serverless functions, queues).

Operational rollout plan (phases):
- Phase 0: internal dogfood (2 weeks): enable in staging, validate resume success, validate cost impact for long-running streams.
- Phase 1: opt-in beta (4–6 weeks): SDKs add opt-in flag; beta customers invited. Monitor resume metrics and early bugs.
- Phase 2: default-on for new SDK versions (8–12 weeks): remove opt-in for new SDKs but keep server-side flag to disable per-customer.
- Phase 3: GA and console exposure (after validation): show resume analytics, allow TTL configuration for Enterprise.

Open questions / risks:
- Client identity on resume: how strict should we be about IP / device rotation during resume? Recommended: allow resume if project/api-key matches and optionally require ephemeral client-sig for higher security flows.
- Cost model: resumed token delivery increases tokens billed to original call; need sales + billing guidance on how to present to customers.
- Tool adapter adoption: risk of partial adoption leading to opaque failure modes. Mitigation: provide adapter shims and a testing harness.

Implementation notes / next steps:
- Infra: small in-memory checkpoint store per front-end node with optional short-lived persistence (Redis TTL-backed).
- Runtime: stream frames labeled with frame_id + checkpoint markers; emit receipts for tool calls synchronously with the frame that triggers them.
- SDK: JS and Android/IOS helpers, with default auto-resume and a minimal public API.
- Docs: design doc on Confluence, migration guide, recipe: integrating with a webhook-based tool backend.

Quick sketch: developer flow (JS):
1) const s = client.startStreaming({enable_handoff: true, sink: 'json-action'});
2) s.on('onFrame', f => renderPartial(f));
3) // client goes offline
4) // later: const resumed = client.resumeStreaming(handoffToken, lastFrameId);
5) resumed.on('onCheckpoint', checkpoint => hydrateState(checkpoint));
6) // client sees tool receipts and dedup logic runs automatically

Appendix: short test checklist for dogfood
- Network toggle tests (chrome devtools) — resume within TTL
- Background tab to foreground resume — mobile & desktop
- Tool adapter dedup test — repeated resume attempts with same idempotency_key
- Checkpoint frequency edge cases (very high-frequency structured outputs)
- Billing label verification in Console

Notes to reviewers:
- This is intentionally conservative on server retention. If the team is comfortable we can expand TTL for specific use-cases in Phase 1.
- Asking infra and serving runtime for a feasibility check for a lightweight Redis-backed checkpoint store (ops cost estimate)
- Requesting SDK owners for estimate on JS/Android/iOS implementation effort (ETA request: 3 weeks for JS prototype).
