Mixed-Quant Fallback Scenarios and Scheduler Proposals (Draft)

Purpose
This doc captures an experimental set of execution-path proposals for mixed-precision inference in the serving runtime (INT8, FP8, GPTQ, AWQ). It focuses on: kernel constraints, KV cache interaction, scheduler signals that should drive fallback, and a small set of reproducible scenarios we can use to validate behavior in the staging environment. This is intentionally pragmatic: lightweight heuristics + strict safety boundaries.

High-level goals
- Maintain correctness (bit-identical or acceptable tolerance) for models that are sensitive to precision changes.
- Maximize throughput and cost savings by using lower-precision kernels where safe.
- Ensure predictable latency SLOs via explicit fallback triggers and fast rollback.
- Minimize KV cache incoherence and avoid cross-precision cache pollution.

Scope and non-goals
- Scope: transformer decoder-only and encoder-decoder families used in our catalog; runtime-level kernel selection and scheduling policies; KV cache state management rules for precision transitions.
- Non-goal: detailed per-model quantization recipes (those belong to model-onboarding docs). This doc defines runtime constraints and observable tests.

Assumptions and constraints
- Kernel vendors expose capability flags: supports_fp8, supports_int8, supports_gptq_layout, supports_awq_ops. We rely on the capability flags provided during node registration.
- Models are annotated with metadata: quantization_compatibility: [int8, fp8, gptq], sensitive_layers: [] optionally. Model owners can mark layers as "precision-sensitive" to prevent low-bit execution there.
- KV cache entries are typed: cache_precision = {fp32|fp16|fp8|int8-packed}. Mixing cache precision in place is unsupported; transitions must follow explicit migration or copy rules.

Kernel capability matrix (runtime view)
- INT8 kernels: fast GEMM path, requires per-channel scales; limited dynamic range, good latency for short sequences.
- FP8 kernels: additional exponent handling; improved dynamic range vs INT8 but higher per-token cost than INT8.
- GPTQ kernels: layout-optimized for non-uniform quant tables, require special dequantization step per layer; often slightly slower than FP8 but much lower memory.
- AWQ kernels: faster than GPTQ for some weight layouts, but failure modes exist when activation distributions shift.

Contraints and compatibility rules (summary)
- A node that registers with supports_int8=true cannot accept an in-flight request tagged cache_precision=fp16 unless the runtime will transparently convert the cache to the node's working precision before executing. Conversion is only allowed for FP16 <-> FP32, not for low-bit formats without explicit copy.
- When routing a request to a lower-precision kernel, we must ensure model metadata allows it and that the current context length and prefix characteristics match the model's validated distribution.
- No mixed-precision within a single layer execution unless kernel explicitly supports mixed compute (e.g., FP8 compute with FP16 accumulation). We mark such kernels with supports_mixed_accum=true.

Execution paths and fallback triggers
We define three canonical execution paths:
1) Preferred low-bit (fast path): node supports requested low-precision kernel, model allows it, KV cache stored in compatible format. Execute with low-bit kernels.
2) Opportunistic low-bit with local conversion: node supports low-bit compute but KV cache is FP16/FP32. If model has small prefix and conversion cost <= latency slack, runtime may convert a copy of the prefix into low-bit cache for the request only (no persistent mutation).
3) Safe high-precision fallback: If any constraint fails (unsupported kernel, model-marked-sensitive layer, cache incompatibility without acceptable conversion cost), route to a high-precision (FP16/FP32) node.

Fallback signals (detailed)
- Kernel missing: node capability does not include kernel required by model's requested quant path -> immediate fallback.
- Layer sensitivity violation: model annotated a sensitive layer which would be executed in low-bit -> fallback.
- KV cache layout mismatch: cached prefix is low-bit incompatible and conversion would exceed latency budget -> fallback.
- Runtime instability: sustained error rates > 1% on a node for a given kernel type -> cooldown and fallback to stable variant.
- Output-quality regression signal: eval monitor triggers quality drop on a prompt set -> rollout to conservative path for affected route.

KV cache rules and lifecycle
- Cache is typed at insertion. When a request causes a change in precision, the runtime will never mutate existing cached entries in-place to a different precision. Instead it writes a derived entry under a new key containing precision tag. This prevents corruption for concurrent requests.
- Cache key format: model_id|prefix_hash|precision_tag|length_bucket. length_bucket is coarse (e.g., 0-32,33-128,129-512) to keep cache hit rates reasonable across slight length variations.
- On opportunistic conversion (execution path 2), we create temporary cache entries with TTL=short (e.g., 10s) scoped to the requestor to avoid polluting global cache with low-hit derived entries.
- Migration policy: background job can attempt to backfill derived low-bit cache entries for very hot prefixes when node capacity and cost analysis suggest benefit. Migration must be reversible and logged.

Scheduler signals and policy proposals
- Core scheduler inputs per request: model_id, requested_precision_hint, measured_latency_budget, prefix_length, cache_hit_tag, route_priority.
- Node scoring formula (proposal): score = w1*latency_percentile(95) + w2*cost_per_token + w3*compat_penalty + w4*cache_affinity. Lower is better. We will start with weights: w1=0.5, w2=0.25, w3=0.15, w4=0.1.
- Compatibility penalty: infinite if kernel unsupported or sensitivity violation present. Otherwise small penalty if conversion required.
- Cache affinity: nodes that already hold matching precision-tagged cache for prefix get negative bonus. This drives hotspot locality.
- Pre-warming: when a route is marked canary->production during rollout we pre-warm low-bit cache derivations on a subset of nodes to reduce first-request conversion latency.

Example scenarios (repro steps)
- Scenario A: Short-chat (prefix 12 tokens), model marked compatible with int8. Node supports int8 but lacks int8-prefixed cache. Expected path: opportunistic conversion of prefix to int8 (temporary cache), execute int8 kernels, succeed with 20% token cost reduction vs fp16.
- Scenario B: Long-context summarization (prefix 1024), model compatible with fp8 but not int8. Node supports fp8. Expected path: prefer fp8 kernel, but if node under load and fp16 nodes available with lower latency penalty, scheduler may choose fp16 fallback to maintain SLOs.
- Scenario C: Model has one sensitive layer annotated. Node with awq attempts to run awq kernels but would hit sensitive layer -> runtime forces per-layer high-precision computation for that layer (if kernel supports mixed-accum). If mixed-accum not supported, route entire request to high-precision node.

Testing and validation plan
- Unit tests: kernel selection logic, cache key derivation, fallback trigger evaluation.
- Integration: synthetic replay harness with mixed precision flags to validate cache isolation and conversion budgets.
- Staging perf tests: run A/B comparing default (fp16) vs opportunistic int8 vs fp8 across 5 representative models. Measure token cost, p95 latency, and quality delta on held-out prompts.
- Chaos test: simulate node-level kernel crash on awq/gptq kernels and ensure scheduler cooldown triggers and fallbacks execute cleanly.

Open questions / trade-offs
- How aggressive should background cache backfills be? More backfills = lower latency but higher total storage and conversion cost. Need a policy tied to traffic heat and predicted ROI.
- Should we permit in-place persistent cache migration when a model owner explicitly opts in? This would simplify repeated-opportunity low-bit serving for a model but poses risk for clients that expect cache stability.
- Do we allow mixed-precision within a single layer if hardware supports it? Early experiments show benefits but require strict validation for numeric parity.
