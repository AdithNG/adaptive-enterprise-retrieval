Attention chunking and memory reclamation interactions in mixed-precision MoE (Qwen) - lab notes

Summary:
These are exploratory notes from a week of profiling mixed-precision MoE inference on Qwen-family weights with long-context workloads (8k-32k tokens). Primary focus: how attention chunking strategies interact with per-request memory reclamation and allocator behavior at inference time, and how that amplifies MoE routing memory imbalance. Goal: identify low-risk mitigations for production serving runtime (hosted + dedicated) that avoid large model rewrites.

High-level observations:
- Attention chunking (sliding window / block-attention) reduces peak working set but introduces more frequent temporary buffers and repeated kernel launches. On H100/A100 this increases cudaMalloc/cudaFree churn unless a pooling allocator is used.
- Mixed-precision (fp16 / bf16 compute, fp32 accumulation) reduces raw memory for activations ~1.9x vs fp32 but does not change number of allocations. Fragmentation and allocator overhead become the dominant source of latency variance for small/medium batches.
- MoE routing amplifies this: per-expert buffers and gather/scatter ops create skewed memory footprints per request. Under chunked attention, the router lifecycle (compute routing -> dispatch to experts -> gather) causes transient memory spikes per chunk that are not well-accounted by simple peak tracking.
- On Qwen-Base (13B) with MoE-extended experts (simulated by routing layer), the worst-case transient exceeded available scratch on A100-40GB with 32k sequences in 1-shot tests without pooling.

Experiment setup (concise):
- Models: Qwen-13B baseline, Qwen-13B + MoE-style sharded-experts shim (custom router layer used to reproduce memory patterns), Llama-2-13B and Mistral-7B used as quick crosschecks.
- Hardware: A100-40GB, H100-80GB; single-GPU runs for deterministic profiling.
- Runtime: PyTorch 2.1 + Triton kernels, custom serving runtime layer (runtime branch: feature/allocator-pool-experiments). FlashAttention v2 and Triton block attention variants tested.
- Precision: fp16 compute (autocast), float32 accumulation where applicable; small runs with int8 quant disabled to isolate memory churn.
- Workloads: synthetic long-context sequences: 8k, 16k, 32k tokens; batch sizes [1,2,4]; prompt shapes: long-prefix-only vs interleaved turns.

Key micro-profiling captures (representative):
- Kernel distribution (8k seq, batch=1, Qwen-13B+MoE shim, A100):
  * Attention-block kernels total 42% of token time (single-step average 4.1ms/token).
  * KV allocation/free overhead (cudaMalloc/cudaFree) contributed ~1.2ms per chunk on average when pooling disabled.
  * Routing gather/scatter kernels added 18% of token time, but had large tail latencies (p90 2.7x p50) due to memory thrashing.
- GPU memory usage trace (32k, batch=1):
  * Baseline (no pooling): multiple ephemeral allocations at chunk boundaries caused a sawtooth pattern in resident memory; observed spike ~+1.8GB per chunk which sometimes triggered transient OOMs when combined with MoE dispatch buffers.
  * Pooling allocator (per-device, sized pool) smoothed peaks and reduced p95 latency by ~28%, p99 by ~40%.
- Occupancy / utilization: repeated tiny kernels (small attention blocks) reduced average SM utilization to ~52% vs ~74% for large fused attention kernels. Launch overheads become non-trivial for 512-1024 token chunks.

Root causes (hypothesis-backed):
1) Allocation churn: chunking splits attention into many short-lived temporaries. Standard CUDA allocator behavior (or default caching allocator behavior in older Torch versions) can still invoke small device allocations that fragment.
2) Router/expert imbalance: routing creates per-expert scratch regions with size proportional to selected tokens; because chunking interleaves dispatches, some chunks concurrently require multiple expert scratch segments leading to higher instantaneous memory than predicted by average expert load.
3) Kernel launch inefficiency: smaller chunk sizes lead to smaller GEMM shapes and lower peak GPU efficiency; combined with more launches, overheads are additive.
4) Mixed-precision partials: while fp16 reduces activation size, accumulation/softmax steps still need fp32 intermediates for numerical stability, so not all temporaries shrink.

Mitigations tested and results:
- Fixed-size per-request KV preallocation: allocate max-KV buffer at request start (based on seq_len and model) instead of cumulative chunk allocations. Result: reduced allocation churn; p95 latency improved but steady-state resident memory increased slightly. Tradeoff acceptable for dedicated nodes.
- Device pooling allocator (pre-reserved pool per GPU): prevented cudaMalloc churn and smoothed memory curve; combined with best-effort trimming reduced p99 latency. On H100 this is highest-impact change.
- Routing-aware scheduling: two variants tested:
  * Batch-first routing consolidation: collect routing decisions for N chunks and then dispatch experts in consolidated batches to amortize per-expert scratch. Good throughput but increases tail latency; not ideal for low-latency SLOs.
  * Token-flow-based backpressure: limit number of in-flight chunks that can trigger expert dispatch for a single request to reduce transient memory spikes. Reduced p99 OOMs but required careful tuning to avoid big latency amplification under load.
- Chunk size tuning heuristic: dynamic chunk sizing by recent kernel timings (increase chunk size when kernels are small to regain efficiency, shrink when memory pressure high). Gains: ~10–18% throughput improvement vs static chunk size across variable prompt shapes.
- Fuse attention + routing kernels: prototype Triton fusion reduced intermediate buffers and cut routing kernel time by ~22% in microbenchmarks. Non-trivial engineering cost and hard to generalize across architectures.

Practical recommendations for serving runtime (priority list):
1) Immediate (low risk): enable per-GPU pooling allocator with configurable bucket sizes; expose toggle to customers. This yields the largest reduction in p95/p99 spikes with minimal model changes.
2) Short-term (engineering effort): implement per-request preallocation of KV buffers when request seq_len > threshold (e.g., 8k). For Dedicated capacity we can make threshold conservative.
3) Medium-term: routing-aware scheduler in runtime that caps concurrent expert dispatches per request and consolidates small dispatches within micro-windows (e.g., 2–5 chunks). Provide conservative defaults and opt-in aggressive consolidation for throughput-optimized tiers.
4) Longer-term: investigate kernel fusion (attention + routing dispatch) and explicit scratch pools for experts. Consider handing off heavy fusion work to Triton kernels maintained in serving-runtime and enabled per-model via model catalog flags.

Open questions and follow-ups:
- Is the observed allocator behavior reproducible across other versions of PyTorch / CUDACacheAllocator? We saw differences between Torch-2.1 and Torch-2.2 in dev runs; need to pin stable baseline for hosted API.
- How does real customer traffic (interleaved short/long prompts) change optimal chunk heuristics? Need live traffic sampling to tune dynamic chunking policy.
- Could we provide a model manifest hint (from model onboarding) to declare that model uses MoE-like routing so runtime can enable special scheduling? This would be similar to model-quantization flags.
- Quantization interaction: we disabled int8 in primary runs to isolate memory churn; need to rerun with int8 serving codepaths to confirm no regressions.

Closing note:
This run highlighted a common theme: algorithmic optimizations (chunking, MoE routing) that reduce asymptotic cost can introduce operational complexity in the allocator and scheduler layer. For production-serving, runtime-level fixes (pools, prealloc, scheduler heuristics) are the fastest path to stable improvements. Kernel fusion and deeper model changes are higher ROI but require longer cycles and careful gating.

If we want to push further, next immediate action is the 48-hour pooled allocator A/B test and then the per-request KV prealloc prototype on dedicated fleet.
