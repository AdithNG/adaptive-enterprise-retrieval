Cascade Financial Group

Cascade Financial Group is evaluating Redwood Private (VPC) for internal support-agent + enterprise doc-search workloads. Key constraints: regulated environment, strict maintenance windows, limited/controlled egress, and strong rollback guarantees. They require preflight checks that can block upgrades (cluster health, storage headroom, RBAC/SSO reachability, DB connectivity, TLS/DNS) and auditable upgrade artifacts suitable for CAB/change tickets. They prefer N-1 -> N upgrade support with a deterministic, operator-driven rollback path and clear maximum time-to-restore targets. They also require an artifact mirror approach inside their VPC (private container registry + chart repo/mirror) with signature/checksum verification; no dependency on public internet during upgrade execution.
Account: Cascade Financial Group (CFG). Regulated financial services, heavy internal governance.

Current state / motivation:
- Building LLM-powered internal assistant for Tier-1 support + policy Q&A. Secondary: knowledge search across internal docs, and meeting summarization for ops.
- They tried a prototype using managed endpoints but got blocked on networking + audit requirements.

Deployment + networking constraints (VPC Private):
- Customer-managed AWS VPC. Must avoid public egress during routine ops; exceptions require security sign-off.
- Strong preference for using VPC endpoints / private links for any required services.
- Artifact distribution must work via: private ECR (or equivalent), internal chart repo mirror, and/or S3 bucket behind a gateway endpoint.
- They asked explicitly: 'Can upgrades run if we temporarily disable NAT?' -> Answer expected: yes, with internal mirrors/bundles + installer verification.

Maintenance windows / change management:
- Standard maintenance window: Sundays 02:00–05:00 ET (hard stop). Additional windows possible quarterly with 2-week notice.
- CAB packet requires: planned from/to versions, risk score, precheck output, backup confirmation, rollback steps, and validation checklist.
- Named approvers required: SRE lead + Security change manager.

Rollback expectations (must-have):
- Need deterministic rollback entry points (operator-triggered) with explicit definition of what 'rollback complete' means.
- Asked for a written guarantee that rollback is supported for N-1 -> N upgrades and that tooling will preserve an auditable trail.
- Target: ability to restore service within 30–60 minutes if an upgrade fails mid-flight (esp. DB migration scenarios).

Prechecks (their 'blockers' list):
- Cluster health: nodes Ready, critical pods healthy, no pending CSRs, disk pressure.
- Storage headroom: must block if < 25% free on persistent volumes used by DB + control plane.
- DB connectivity + migration lock timeout behavior (they have had incidents from long locks).
- SSO reachability: SAML/OIDC endpoints must be resolvable from cluster; warn vs block debated, but security wants this blocking for prod.
- Artifact availability: all images/charts/manifests present in internal mirrors; checksums/signatures verified before any changes.

Audit logging & evidence:
- Wants upgrade lifecycle events: upgrade start, prechecks pass/fail, backup complete, plan executed, rollback invoked, rollback complete, plus actor identity.
- Retention: 1 year searchable in their SIEM (Splunk). Need export/forwarding story.

Product fit notes:
- They are aligned with in-place upgrade + rollback approach (vs blue/green) if auditability is strong and prechecks are strict.
- They asked for a sample 'upgrade plan' JSON/artifact to attach to change tickets.

Open questions:
- Confirm whether they will accept mirrored artifacts + signed manifests (preferred) vs fully offline bundles (not required today, but might be a future ask).
- Clarify which components must be backed up (DB, config/state, secrets refs) vs customer-managed secrets systems.
