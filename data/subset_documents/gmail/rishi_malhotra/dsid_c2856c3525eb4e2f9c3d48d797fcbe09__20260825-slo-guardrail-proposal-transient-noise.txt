Rishi / Ben — looping in a few practical constraints from Product & SRE. I'll keep this high level so Emily has something procurement can include in the term sheet.

Proposal refinements (operational + contract-friendly language):
- Measurement windows: keep p50 as rolling 24-hour median measured at the per-account request level (Redwood measurement point = time from request ingress at API gateway to final token emission acknowledgement). Note: client-side network latency is excluded; we can add an optional client-side agent if Arcadia wants end-to-end.
- Pilot behavior: agree to a pilot-phase p95 using a 14-day rolling window (as requested). After pilot completion (defined as a month at target stability), p95 rolls to standard 7-day rolling window. We will include a rollback clause if variance persists.
- Transient/noise carveout (machine-readable summary): carveouts apply when ALL of the following are true for a contiguous interval:
  * measured account-level QPS > 3x baseline QPS (baseline = 7-day median QPS)
  * outage interval duration < 15 minutes OR affected request share < 5% of account traffic in that interval
  * the interval does not overlap a scheduled maintenance window
  Intervals meeting the above will be excluded from the rolling percentile aggregation. We'll provide a JSON machine-readable rule set and a sample exclusion report during onboarding.
- Sampling & min-sample-size: to avoid noisy quantiles, p95 calculations require at least N=200 successful requests in the aggregation bucket; otherwise we fallback to a longer window for p95 computation.
- Credits: propose standard monthly credit slabing triggered when p95 misses more than 0.5% of the aggregated measurement days in a 30-day period (we can provide the precise credit table in the amendment).

Operational notes for Ben (SRE): we will implement a canary where Arcadia traffic is initially served with the standard runtime and a shadow of quantized variants for 48 hours; if tail increases by >15% during canary we'll auto-fallback.
