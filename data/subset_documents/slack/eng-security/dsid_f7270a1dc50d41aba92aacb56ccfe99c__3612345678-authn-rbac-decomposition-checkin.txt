sam: Quick sync — we need to finalize the RBAC decomposition for service auth. Thinking about making a small, orthogonal surface for service-to-service tokens that is separate from user API keys.

lisa: +1. can you sketch the constraints again? we have to support: background jobs, external partners, and user-facing API keys. also we need a migration path for existing long-lived keys. :thinking:

rajesh: Constraints that matter to me: least-privilege by default, low-cost path for internal high-throughput calls, and explicit operator identity for orchestration tasks. We should avoid exploding the number of token types.

marco: Proposal: two surfaces — "api_key" (user-facing, human-managed, project-scoped) and "cap_token" (machine-oriented, capability-bound, short TTL, can be project or org scoped). cap_token carries a small set of capability labels instead of full role graph. Keep role evaluation on the control plane for long-lived tokens only.

lisa: I like capability labels for perf. how do we map capabilities to routes? e.g., can/call:invoke_model, can:read_metrics etc.

rajesh: Exactly. We make a per-route capability whitelist. Runtime checks are O(1) membership tests on the token claim. For operations that need richer context (billing, audit), we still call the authz service async or attach a signed proof.

sam: Example token payload (cap_token):

```json
{
  "sub": "svc:ingest-worker-12",
  "iss": "redwood-auth",
  "exp": 1712340000,
  "caps": ["ingest:write", "prefix:cache:read"],
  "scope_kind": "project",
  "scope_id": "proj_78a"
}
```

marco: Runtime enforcement plan: data plane services only validate signature + caps membership + scope match. Control plane maps capabilities -> allowed routes and can push route-level deny-lists. This keeps hot path cheap.

lisa: What about delegation / exchange? Some workers need to act on behalf of a user and inherit user-level capabilities for a single operation.

rajesh: We add a short-lived delegated bearer token flow. Operator (service) holds cap_token and can request a delegated token with an additional claim `on_behalf_of:user:123` if the operator is permitted by policy. Delegated tokens are single-use (or 1-2 minute TTL) and carry combined caps intersection.

sam: Migration notes for existing long-lived API keys:
- Backwards compatible header: keep `Authorization: Bearer <key>` working.
- For keys that look machine-owned (naming heuristics + last-used patterns) surface a suggested `cap_token` migration modal in console.
- Hard deadline plan: rotate to require `x-rdwd-actor` header on internal-only endpoints for non-migrated keys (canary to 10% traffic).

marco: Example CLI to mint a cap_token for a service with allowed caps (ops only):

```bash
rdwd auth mint --subject svc:ingest-worker-12 --caps ingest:write,prefix:cache:read --scope project:proj_78a --ttl 3600
```

lisa: How do we represent RBAC for humans? do we keep role graph as-is and translate roles -> caps for tokens?

rajesh: Keep role graph for human users and admin workflows. When a human creates a machine identity, control plane emits a cap_token whose caps are derived from the role graph mapping (a projection). That projection is audited and stored as a small mapping table.

sam: Rollout / canary plan:
1) Implement cap_token mint + validation logic behind feature flag.
2) Add route-level capability mapping in a config store (start with ingest, metrics, model-inference routes).
3) Opt-in beta: internal services request validation only and report mismatches (no enforcement).
4) 10% enforcement canary using header gating.
5) Full enforcement + require migration UX for other keys.

marco: Telemetry: token type, caps count, avg validation latency, mismatches, delegation events. We need SLO of <1ms added to hot path. Should be achievable with local JWKS + memcache for mapping.

lisa: Auditing: store the mapping event (role -> caps) and the mint event (who minted cap_token, which source role). Keep 90 days by default.

rajesh: Security checks: require KMS signing for cap_tokens, enforce rotation, and block cross-project scope unless explicit operator grant. Also deny `admin:*` style caps in cap_tokens unless explicit justification (manual review).

sam: Open questions:
- revocation semantics for cap_tokens w/ short TTL (do we need immediate revoke?)
- admin caps in machine tokens (policy vs ban)
- how granular capabilities should be (coarse vs many tiny caps)

marco: My take: short TTL + revocation list for emergencies is fine. For day-to-day revocations rely on TTL + reissue. Granularity: start medium (route-level) and only split caps if real customer need arises.
