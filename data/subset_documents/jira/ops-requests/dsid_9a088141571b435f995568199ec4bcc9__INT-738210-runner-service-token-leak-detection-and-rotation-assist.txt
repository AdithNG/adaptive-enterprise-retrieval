Runner service account token exfiltration alert: rotate tokens and validate CI access paths

Issue summary:
Security monitoring flagged potential exfiltration of a long-lived service token tied to a fleet of ephemeral CI runners. Alert originated from log anomaly: identical token used from two distinct datacenter IP ranges within a 5 minute window. Impact: potential unauthorized access to private repositories and deployments; immediate mitigation required for release pipelines scheduled tonight.

Impact:
- Nightly release pipelines (release-nightly) and a handful of ad-hoc build jobs are at risk of unauthorized usage.
- No confirmed production changes yet, but token reuse pattern suggests credential may be leaked to an external CI job runner.

Environment:
- prod control plane, primary runner pool in us-east-1, ephemeral runners launched via autoscaler with service-account tokens minted by internal token-service.

Steps to reproduce / observed sequence:
1) 2026-03-13T18:02Z: Security alert (Evidently: auth-anomaly-20260313-17) flagged token XXXXXX-XXXXXXXXXXXXXXXX used from IP A and B.
2) Investigated runner logs: token XXXXXX appears in runner bootstrap logs for runner-id r-3487 and r-3491.
3) Token issuance log shows token minted by token-service for service-account ci-ephemeral-deployer at 2026-03-13T17:58Z with TTL 24h.
4) Access patterns include git fetch and artifact upload attempts to s3-bucket "ci-artifacts-prod".

Immediate requests:
- Rotate all active tokens for service-account ci-ephemeral-deployer and issue short-lived replacements (1h TTL) for any upcoming scheduled jobs.
- Block any outstanding runner sessions that present the old token.
- Audit artifact uploads and git pushes between 2026-03-13T17:50Z and 2026-03-13T18:20Z.

Timeline and hypotheses:
- 2026-03-13T17:58Z token minted by token-service (log id ts-98231).
- 2026-03-13T18:02Z security alert for token reuse from multiple geo-ip blocks.
- Hypothesis A: token printed into a job log or artifact and then scraped by a scanning service or malicious actor.
- Hypothesis B: compromised runner bootstrap image contained a hardcoded token (unlikely, but check image digest).
- Hypothesis C: token-service issued a duplicate due to race and same token reused on two runners (race condition in token-service code).
Findings so far:
- Runner bootstrap scripts do not print tokens intentionally; however, one community script in customer templates folder was discovered in an older job that echoed env on error (CI job id 77312).
- Image digests for r-3487 and r-3491 match the current official ephemeral-runner image: sha256:fdc9..., no unauthorized modifications.
- Token-service code review shows a retry path that can return the same token if request ID deduplication occurs; engineering hypothesis plausible.
