OAuth refresh-loop prevents Jenkins job triggers for service CI user

Issue summary: Scheduled Jenkins pipelines triggered by the internal service account 'ci-bot@redwood' are failing intermittently. Jobs start, then immediately fail with 401 from the token refresh endpoint, causing downstream deploy steps to abort. Impact: Several release pipelines and nightly jobs are blocked for multiple teams.
Multiple teams unable to run Jenkins release and nightly pipelines. Automated canary promotions are failing; manual intervention required for builds created between 2026-03-10 01:15 UTC and ongoing.
1) Configure Jenkins job to use 'ci-bot@redwood' service account via Okta OAuth token exchange.
2) Trigger job via SCM webhook or scheduled timer.
3) Observe job obtain access token then fail on refresh call approximately 15 minutes after start with 401 unauthorized.
4) Reproduced on multiple Jenkins masters in us-west cluster and on a standalone curl against the token refresh endpoint using stored refresh_token.
5) Temporary workaround: generate a long-lived API key for the job and use that instead of OAuth refresh flow (manual change).
2026-03-10T01:17:12Z ERROR token-refresh-service 401 RefreshTokenInvalid: refresh token rejected for client_id=jenkins-internal
2026-03-10T01:17:13Z WARN jenkins.pipeline Step 'deploy' aborted due to auth failure (401)
Okta audit: 2026-03-10T01:16:58Z EVENT policy.evaluation Evaluated user ci-bot@redwood: matched policy 'Session Lifetime > 10m' applied to group 'all-Employees'
Initial hypothesis: Jenkins client misconfigured with wrong client_secret or token endpoint. Rejected after cross-checking client config and successful initial token issuance.
Correlated Okta audit logs showing policy evaluation exactly when refresh tokens were rejected. The policy 'Session Lifetime > 10m' was edited on 2026-03-09 and unintentionally included attribute selector matching service-account group due to a wildcard in rule scope.
Token refresh flow: access_token issued successfully, refresh fails when Okta policy returns 'invalid_session' for refresh_token because service account considered a human session with too-short lifetime.
Temporary mitigation by token service permit rule showed pipelines succeeded, confirming policy mismatch as root cause.
Related config: Jenkins OIDC client uses refresh_token rotation; rotation tokens are short-lived if session lifetime policy applies. Service accounts must be excluded from that policy.
Repro steps executed in staging using a cloned service account to test policy change impact before applying to production.
No evidence of credential compromise; this was a policy scoping error from Identity team's recent change.

Permanent fix: Identity team updated the Okta session lifetime policy to exclude OU 'service-accounts' and replaced the overly-broad group selector with explicit include/exclude rules. Token service and Jenkins clients were rolled to accept rotated refresh tokens under the corrected policy. Post-deploy verification: 10+ scheduled jobs executed between 2026-03-12 02:00-04:00 UTC successfully. Next steps: add automated policy unit tests, create a runbook for service-account policy changes, and schedule an audit of Okta policies to catch similar regressions.
