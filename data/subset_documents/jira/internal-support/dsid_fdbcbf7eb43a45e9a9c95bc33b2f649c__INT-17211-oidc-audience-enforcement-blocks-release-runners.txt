OIDC audience enforcement update causing GitHub self-hosted runners to fail token exchange for release pipelines

Issue summary:
An identity provider change (OIDC audience enforcement) in our cloud IAM configuration started rejecting OIDC tokens presented by GitHub self-hosted runners used for release pipelines. The immediate symptom is that release jobs using the standard OIDC token exchange to obtain short-lived cloud credentials are failing with an invalid audience error.

Impact:
- Release pipelines (deploy/* and canary/*) running on self-hosted runners in the 'release-pool' are failing to obtain cloud credentials, blocking all production deploys.
- No data loss, but rollout windows missed; manual approvals piling up.
- Affected teams: release-engineering, infra, platform-ops.

Environment:
- environment: prod
- regions: us-west1 (primary release runners), us-east1 (fallback)
- components: ci-runner, oidc-identity-provider, iam, vault

Observed behavior:
- Jobs fail during the token exchange step with errors similar to: "token exchange failed: invalid_claim: aud does not match allowed audiences"
- GitHub Actions logs show the OIDC token was minted and attached, but cloud provider API returns 401/403 on the exchange call.
- Short-lived credentials are not provisioned and tasks stop at the deploy stage (no infra API calls are performed).

Steps to reproduce:
1) Trigger any release pipeline on a self-hosted runner from the release-pool.
2) Observe the step that performs 'gcloud iam workload-identity-pools create-cred' (or equivalent AWS AssumeRoleWithWebIdentity) fail.
3) Inspect runner logs and cloud audit logs.

Relevant logs / snippets:
- GitHub runner: "OIDC token acquired: iss=https://token.actions.githubusercontent.com, aud=repo:redwood-inference/release-pipeline:ref:refs/heads/main"
- Cloud IAM audit: "denied request: invalid claim 'aud', expected one of [sigstore, sts.myorg], got 'repo:redwood-inference/release-pipeline:ref:refs/heads/main'"
- Runner debug output (token introspect): "{\n  \"iss\": \"https://token.actions.githubusercontent.com\",\n  \"sub\": \"repo:redwood-inference/release-pipeline:ref:refs/heads/main\",\n  \"aud\": \"repo:redwood-inference/release-pipeline:ref:refs/heads/main\",\n  \"exp\": 1710700000\n}"

Hypothesis / investigation notes so far:
- On 2026-03-11 at ~23:40 UTC, a cloud security change deployed stricter audience validation rules to the OIDC trust configuration for our workload-identity pool. The change reduced allowed audiences to a small set of well-known strings used by internal automation (sigstore, sts.myorg).
- GitHub's default OIDC audience for repository tokens includes the repo+ref pattern; our runners are presenting that aud value and failing validation.
- This is not a GitHub-side regression; token shape unchanged. The enforcement change caused previously-accepted aud values to be rejected.
- The change was rolled via <confluence>/cloud-iam/audience-hardening-2026-03-11 and tracked in INT-17099 (internal).

Temporary workaround applied:
- Platform-ops reverted the audience enforcement rule for the workload-identity pool to the previous permissive config (rollback at 2026-03-13 02:15 UTC). This allowed release pipelines to proceed while we draft a long-term fix.
- Workaround is a temporary permit list that includes repo:* audiences.

Long-term remediations being considered:
1) Update workload-identity provider mapping to explicitly accept GitHub repo audiences (add pattern support) and document the allowed audience list.
2) Switch release pipelines to use a centralized short-lived broker token (trusted audience string) minted by our internal 'sts.myorg' service that exchanges GitHub OIDC tokens on behalf of runners.
3) Update runbooks and enforce a compatibility test when changing any IAM policy that affects OIDC audience checks.
