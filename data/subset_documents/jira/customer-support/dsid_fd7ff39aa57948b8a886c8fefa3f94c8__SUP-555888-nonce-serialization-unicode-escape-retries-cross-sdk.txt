Intermittent duplicate function/tool invocations due to nonce serialization differences over websocket retries

Issue summary: Customer reports rare duplicated external tool/function invocations when retry logic triggers over websocket-based streaming. Duplicates are observed only when the client reconnects and the retry includes an idempotency nonce that contains non-printable/control characters or unicode escape sequences.

Impact: Intermittent duplicate side effects (duplicate charges/duplicate downstream jobs) causing customer concern; affects a small subset of requests that embed binary or escaped characters in the client-generated nonce field.

Environment: prod us-east, customer using Redwood TS websocket streaming SDK (v1.6.x) and Python SDK (v0.9.x) interfacing with a serverless webhook middleware. Dedicated consumer account on enterprise tier.

Steps to reproduce (customer test harness):
1) Open a TS websocket connection to /v1/streams with: client-provided nonce containing JSON-escaped control sequences (e.g. "idempotency_nonce": "op-\u0000-abc\u0000\n").
2) Trigger a function/tool call in the stream; intentionally drop the websocket frame mid-response to force client reconnect and automatic retry.
3) Observe server logs for two separate function invocations for the same logical request ID. The client thinks it retried the same nonce; server sees a different canonical nonce form.

Observed logs (snippet):
- Incoming nonce (raw ws frame): "op-\\u0000-abc\\u0000\\n"
- Normalized header (api-gateway): "op-\u0000-abc\u0000\n"
- Idempotency lookup failed -> created new execution record
- Duplicate side effect executed

Temporary workaround: Ask customers to avoid unescaped control characters in client-generated idempotency nonces; use base64 or hex-encoded nonces, or switch to HTTP request with Idempotency-Key header which normalizes reliably.

Why this happened: We found two normalization paths for idempotency tokens:
- WebSocket path: payload is parsed by SDKs which sometimes preserve JSON-escaped sequences as literal two-character sequences "\\u0000" instead of the binary control char. Downstream proxy (edge) then applies a different decode step, turning escapes into actual control characters before the idempotency-store lookup.
- HTTP path: Idempotency-Key header is treated as opaque bytes and goes through a single normalization layer.

This mismatch produces two distinct keys on the server side for the same client nonce depending on whether the escape sequences were converted to literal control characters during transport. The server lacked a canonical normalization step for websocket-origin nonces.
- Reproduced locally using a minimal TS websocket client that deliberately includes JSON-escaped control sequences in nonce.
- Captured wire trace with tcpdump; confirmed the client emitted backslash-u sequences in the websocket payload, and the edge proxy decoded them in a subsequent middleware pass.
- Checked idempotency store (DynamoDB) keys: two distinct items created within 200ms of each other, matching the two different token byte sequences.
- Confirmed similar behavior in Python SDK when using json.dumps with ensure_ascii=True vs ensure_ascii=False; different defaults across SDKs produce different payload encodings.
- Reviewed SDK versions: ts-sdk v1.6.x was not percent-encoding control bytes; python-sdk v0.9.x had a helper that stored the nonce as-is leading to inconsistent encodings across SDKs.
- Root cause: lack of a canonical server-side normalization and inconsistent client-side serialization of unicode/control characters in idempotency nonces over websocket transport.

Long-term fixes:
- SDK changes merged: TS SDK percent-encodes non-alphanumeric chars in idempotency nonces by default; Python SDK added a helper to produce urlsafe_base64 nonces and documentation guidance. PRs: github.com/redwood/ts-sdk/pull/842, github.com/redwood/python-sdk/pull/611.
- Documentation update: "Idempotency nonce best practices" added to Confluence and public docs with examples and recommended validator code.
