ADFS group claim size causes token exchange truncation and service account authorization failures in private deployment

Issue summary:
Acme Analytics' private Redwood deployment started seeing repeated 401/403 failures for scheduled batch workers and some admin console actions after a recent LDAP group-sync. The auth exchange service returns an access token with very large group claims (ADFS/SAML), which appears to be truncated by the edge proxy/ingress when exchanged for an internal service token. Missing group/tenant bindings cause RBAC evaluation to deny requests.

Impact:
- Multiple scheduled batch workers fail to start jobs (impacting nightly report generation).
- Some customer admins intermittently cannot access the private console or impersonate service accounts.
- Repro rate: ~90% for affected workers after heavy LDAP membership sync.

Environment:
- Private deployment (VPC) in us-west region
- Redwood release: private-agent v2026.02.3
- Identity provider: ADFS 2019 via SAML 2.0 assertions
- SCIM sync: upstream LDAP -> IdP groups expanded into SAML Group attribute

Steps to reproduce (observed):
1) Trigger SCIM sync from LDAP that populates a user with 800+ nested group memberships.
2) User requests a short-lived internal service token via the standard token-exchange flow (SAML assertion -> Redwood auth service -> internal JWT).
3) Auth service returns a large JWT containing group claim array (~11KB).
4) External edge/ingress (customer-managed) rejects or truncates the Authorization header when proxying to the internal token exchange endpoint.
5) Downstream RBAC code does not see the full group list; tenant-binding role resolution fails and request receives 401/403.

Observed behavior:
- In edge-proxy logs we see downstream requests with Authorization header length reported as "truncated" (proxy debug): "incoming header length 8192 > max_header_size(8192) -> truncated".
- Auth service logs show successful token issuance (full group claim present) but the token received at the internal API is shorter / missing suffix groups.
- SRE trace shows RBAC decision referencing empty role bindings for affected principal.

Expected behavior:
- Token exchange should succeed without header truncation and RBAC should see the full group claim set.

Initial hypothesis:
- The ingress/proxy enforces an 8KB header limit and will either reject or truncate headers above that threshold. Large group arrays from ADFS push token sizes above that threshold.
- Truncation removes tenant-scoped group values necessary for role mapping.

Evidence / Logs (redacted):
- auth-service (issue-time): "issued_token_size=11456 principal=svc-worker-123"
- edge-proxy debug: "Authorization header length: 11456 (exceeds max 8192) -> truncated to 8192"
- internal-api: "jwt parsed groups=0 (expected >200) principal=svc-worker-123"
- customer reported correlation: failures begin after LDAP group cleanup job completed at 02:05 UTC on 2026-03-09.

Temporary mitigation attempted by customer:
- Reduced group expansion in IdP for a subset of service accounts -> jobs succeeded.
- Customer applied an ingress rule to return 431 on oversized headers instead of truncation (caused easier detection but did not resolve RBAC mapping).

Workarounds suggested by Support so far:
- Short-term: Scope SCIM sync to only send tenant-scoped groups (filter out global/irrelevant groups) so tokens remain under header size limits.
- Mid-term: Configure IdP to emit group IDs in a compressed/hashed claim and map them to roles during SCIM provisioning (avoid huge in-token arrays).

Investigation notes:
- Confirmed token size originates from auth-service after assertion processing; not introduced by client.
- Ingress behavior varies: some customer-managed proxies truncate silently, others reject with 431. Both result in RBAC failures but different observability patterns.
- Redwood internal token parsing has no logic to reassemble fragmented Authorization headers; if truncated, mapping fails deterministically.

Next steps recommended:
1) Engineering: add explicit detection of truncated/malformed Authorization headers in internal-api and surface clearer errors (e.g., 431 with instruction to check IdP group cardinality) to avoid silent 403s.
2) Docs/Support: publish guidance for maximum recommended token size and IdP group cardinality for private deployments, include example SCIM filters.
3) SRE/Customer: recommend customer update ingress config to reject (431) large headers instead of truncating, to make failures clear in logs.
4) Product: consider adding alternative group propagation mechanisms (e.g., reference-based claims, group batched lookup post-auth) for private mode.

Requested from Engineering:
- Confirm whether Redwood will support multi-header Authorization reassembly or a server-side fallback for group lookup when token claims are missing.
- Estimate of effort to add explicit truncated-header detection and improved error messaging.

Reproduced with local ADFS testbed. Observed Authorization header length > 11KB. Edge proxies fall into two classes: 'rejectors' (return 431) and 'truncators' (silent truncate to max_header_size). Truncation pattern causes deterministic RBAC denials because tenant group suffixes are at the end of the array. Verified linked issue SUP-412007 describes a related ingress header truncation pattern for admin console 403s; this expands to token-exchange flow for scheduled workers.
Workaround accepted by customer: SCIM filters applied to reduce in-token group cardinality. Engineering to implement header-truncation detection in internal-api and return explicit 431 with guidance. Product/Docs to publish token size guidance. No code rollover yet; target for v2026.03.x.
