Unicode normalization mismatch in idempotency keys causing duplicated tool executions across Python/TS/Go SDKs

Issue summary:
Customer FastQuery AI reports that when their orchestrator retries a request, downstream tool webhooks are occasionally executed twice. The customer observed duplicate side effects (duplicate database writes and duplicate billing events) in ~0.2% of retried requests.

Impact:
- Duplicate tool executions leading to customer-visible side effects (DB inserts) and increased costs.
- Affects dedicated deployment in us-east.
- Customer reports this is blocking a rollout to production for a billing-critical flow.

Environment:
- Dedicated: fastquery-dedicated-1 (us-east)
- SDK versions: python 2.4.1, ts 1.7.0, go 0.9.3
- Request pattern: streaming chat + function/tool calling; orchestrator supplies an idempotency key (UUID-like with emoji / composed characters)

Observed frequency: ~0.2% of retries (customer workload ~500k requests/day).
1) Customer supplied idempotency key with composed Unicode (e.g., 'txn-\u00E9-\u200D\uD83D\uDE80') via SDK header or request parameter.
2) Simulate transient server error (return 502) to trigger client retry.
3) Observe webhook target receiving two POSTs for the same high-level request.
4) Confirm server logs show two tool-execution entries with different idempotency-key header byte sequence.

Notes: reproduction was easier when HTTP/2 and an upstream proxy (edge) were present.
Retries should de-duplicate by idempotency key and not cause duplicate tool/webhook executions.
In a subset of retried requests the idempotency key used by the API and the idempotency key forwarded to the webhook differ in byte-level normalization; the platform treats them as distinct keys and executes the tool again.
Example header values seen in traces:
- client (python sdk): Idempotency-Key: txn-\u00E9-\u200D\uD83D\uDE80  (NFD bytes)
- client (go sdk): Idempotency-Key: txn-\u00E9-\u200D\uD83D\uDE80  (NFC bytes)
- edge-proxy forwarded: Idempotency-Key: txn-%EF%BC%8D-%CC%81-... (partially percent-encoded / folded)
Trace IDs: trace:us-east:0a1b2c3d4e; tool_exec_id: te-20260310-77aa
Relevant server log excerpt (2026-03-10T14:22:07Z):

[serving-runtime] tool_exec START key='txn-\u00E9-\u200D\uD83D\uDE80' bytes=0x746... (different byte seq)
(We saw mismatched hash checksums for the idempotency key in ~12 of 6000 examined retries.)
Support initial triage: confirmed duplicates correlate with idempotency-key byte differences across SDKs when multibyte/composed characters present.
Hypothesis 1: SDKs perform different Unicode normalization (Python SDK sending NFD, Go SDK NFC) leading to different raw header bytes. Verified by instrumenting SDK header serialization.
Hypothesis 2: Edge proxy (FastEdge) performs header folding / percent-encoding on long/complex headers and may split HTTP/2 header frames; header reassembly can introduce different byte sequences. Reproduced with internal edge staging using HTTP/2 and large metadata headers.
Test: reproduced with a minimal script in each SDK sending identical logical keys; captured raw bytes at ingress and at webhook target. Outcome: raw bytes differ across SDKs in ~100% of runs when composed characters included; with plain ASCII UUIDs, no discrepancy.
Correlation: duplicate tool executions only when (a) idempotency key contained composed Unicode, and (b) request passed through HTTP/2 + edge. This matches customer stack.
Reproduced locally using: curl HTTP/2 + header with combined emoji and accent characters; confirmed header normalization changed depending on client runtime and HTTP library used.
Potential mitigation identified: canonicalize idempotency keys to UTF-8 NFC at SDK client before sending, and treat idempotency key equality on the server after applying the same canonicalization. Also, document recommendation to avoid non-ASCII characters in idempotency keys until SDKs are patched.
Related PRs created: sdk-python#487 and sdk-ts#216 add client-side NFC normalization; sdk-go#98 will follow. Pending server-side changes to canonicalize incoming idempotency keys prior to storage/lookup.
Risk: server-side canonicalization requires a migration plan because existing stored idempotency entries were created with prior raw bytes; fix must ensure lookups are tolerant (normalize both stored and incoming).
