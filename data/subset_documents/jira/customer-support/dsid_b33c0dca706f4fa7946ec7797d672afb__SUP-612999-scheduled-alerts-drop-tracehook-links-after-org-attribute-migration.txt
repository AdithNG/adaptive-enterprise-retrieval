Scheduled alerts lose trace context links after org attribute migration

Issue summary:
Customer BrightSearch reports that scheduled alert notifications no longer include links that open the associated trace context from the Console. Instead the alert payload displays a placeholder and the trace link on the dashboard is broken.

Impact:
- Several scheduled alerts fired on 2026-03-09 and 2026-03-10 without trace links; SRE/eng on-call could not quickly jump to traces to investigate regressions.
- Customer says this blocked two incident investigations and increased MTTR.

Environment:
prod-us-east, BrightSearch org id: 987654321, customer on Dedicated plan with route pinning.

Steps to reproduce (observed locally with a BrightSearch test org):
1) Create a saved query panel that includes the tracehook header in response metadata (x-redwood-trace: <trace-id>).
2) Create a scheduled alert using that panel with an evaluation window of 5m and alert action set to send Console notification.
3) Wait for scheduled evaluation (or trigger manually via /alerts/eval endpoint using org header).
4) Inspect alert payload in Console -> Alerts and the link target on the dashboard.

Observed behavior:
- Alert payload shows "trace_link": "<missing>" and clicking "View trace" results in a 404 from the trace service.
- Query logs show join on organization column "org_id" returned empty for rows created after the metadata migration.

Expected behavior:
- Alert payload contains a working deep-link to the trace view for the matched event.
- Dashboard drilldown opens trace context in a new tab.

Notes:
- Customer confirmed they ran the org attribute rename tool last week as part of a metadata cleanup (internal migration from org_id -> org_uuid). They used the runbook but did not run the alert reindex step because it was optional per the runbook.
- This issue appears to affect scheduled alert evaluations and scheduled report exports; ad-hoc realtime queries from Explore still surface traces correctly.

Timeline: After customer's org attribute rename (org_id -> org_uuid) some downstream services continued to reference org_id. We inspected alert-eval templates and saw a hard-coded WHERE x.org_id = :org_id. The saved panel stores tracehook headers referencing trace ids, but the alert-eval subquery that joins traces uses the old column and therefore returned no rows for events written with org_uuid. Reproduced locally by toggling the org mapping flag. A staging PR existed but had not been promoted to prod. We evaluated risk of immediate template change and decided to deploy a translation shim and run a reindex of alert bindings as the least disruptive mitigation.
Mitigation applied: emergency translation middleware added to alert-eval service to map org_uuid -> org_id for the duration of migration.
