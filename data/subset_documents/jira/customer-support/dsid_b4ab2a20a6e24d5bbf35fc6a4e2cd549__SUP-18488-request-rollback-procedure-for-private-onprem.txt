Customer (Northstar Health Systems) is planning an on-prem / air-gapped upgrade of Redwood Private and is requesting a clear, operator-friendly rollback procedure that can be shared internally for change control.

Request details (from customer):
- They need step-by-step rollback instructions suitable for an IT ops runbook, including what is and is not supported (e.g., Helm rollback vs restore-from-backup).
- They require clarity on expected downtime/RTO and what artifacts must be preserved (offline bundle, chart versions, container images, DB backups, PV snapshots).

  - Air-gapped environment (offline bundle only, no outbound registry/chart repo access).
  - Change windows are short (2 hours max) with a hard stop where they must revert.
  - Audit/compliance requires evidence of backups taken and a deterministic rollback path.

What they are upgrading:
- Redwood Private control plane + data plane via Helm in their own Kubernetes cluster.
- Current version: customer reports they are pinned to an N-1 release (exact patch TBD; they mentioned 2.9.x in email).

Customer questions to answer:
1) If the upgrade fails mid-way (e.g., DB migration or control plane rollout), what are the exact steps to revert?
2) Is a Helm rollback supported? If not, what is the supported rollback mechanism?
3) What preconditions must be met to roll back safely (snapshots, dumps, stopping components, etc.)?
4) What data can be lost (if any) and how to verify system health post-rollback?

Support goal:
- Provide an accurate rollback procedure based on current GA capabilities (not aspirational), while aligning with the upcoming upgrade/rollback work so the customer does not build an incorrect internal process.

Draft rollback procedure (customer-facing, current GA):
A. Before upgrade (required to have a rollback path)
1) Ensure you have the full pre-upgrade artifact set stored offline:
   - The offline bundle for the currently running version (charts + images + manifests).
   - Checksums/signature file if provided.
2) Take backups immediately before running the upgrade:
   - Control plane database backup (Postgres logical dump) and verify you can restore it.
   - Snapshot persistent volumes for stateful services (where supported) or capture storage-level snapshots.
   - Export cluster config relevant to Redwood (Helm values, secrets references, cert material references).
3) Record current versions:
   - Chart version(s), Redwood Private version, and installer version.

B. When to rollback
- Rollback is recommended if:
  - Control plane does not become Ready after upgrade within your maintenance window.
  - DB migrations error or exceed your change window.
  - Auth/OIDC integration breaks and cannot be remediated quickly.

C. Rollback steps (supported)
1) Stop further change:
   - Halt any automation applying charts.
   - If data plane rollout is in progress, pause/stop it first.
2) Restore to pre-upgrade backups:
   - Restore the control plane DB from the backup taken immediately before upgrade.
   - Restore PV snapshots (or storage snapshots) for stateful components if they were mutated during upgrade.
3) Re-deploy the previous version artifacts:
   - Re-apply the previous chart(s) and manifests from the pre-upgrade offline bundle.
   - Ensure your image registry points to the pre-upgrade image set.
4) Post-rollback verification:
   - Confirm control plane health checks.
   - Confirm data plane routing works.
   - Confirm audit logs and auth integrations.

D. Explicitly not supported / cautions
- Helm rollback is not supported once DB migrations have applied.
- Do not run older control plane pods against a DB that has been migrated forward.
