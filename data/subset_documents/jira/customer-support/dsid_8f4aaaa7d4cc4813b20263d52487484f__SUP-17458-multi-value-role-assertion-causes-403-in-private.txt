On-prem SAML: multi-value role assertion parsed as single string, causing 403s for private deployment

Issue summary:
Customer on private deployment reports that after SAML assertion exchange several API calls and console actions return 403 Forbidden for users who should have access. The IdP (Okta) emits a roles attribute with multiple values in a single comma-separated string. The on-prem SSO connector appears to treat the entire comma-separated value as a single role label, so RBAC role mapping fails and the user is unauthorized.

Impact:
- Multiple users in FinEdge cannot perform model deployments or view logs via the Redwood Console; API calls from their backend services are also returning 403 when using the SSO-backed session tokens.
- Business impact: blocked deployments and customer-visible service degradation for internal apps; customer classified as private (compliance-sensitive).

Environment:
- Redwood Private (v1.9.3) deployed in customer VPC (us-west-2) using customer-managed control plane.
- SSO provider: Okta (SAML 2.0).
- Connector: sso-connector v2.4.1 (deployed as part of private package).

Steps to reproduce (customer-provided):
1) User authenticates via SAML to the console using Okta.
2) IdP assertion includes attribute `roles` with value: "admin,platform:deploy" (single attribute value containing comma).
3) User completes login and receives session; attempts to call /v1/models (or use console Deploy button) and receives 403.

Observed behavior:
- Connector logs show mapped_roles = ["admin,platform:deploy"] (single element).
- RBAC engine tries to match exact role labels and fails to find "platform:deploy" so denies access.
- No error in SAML handshake; issue arises only at role parsing stage.

Expected behavior:
- Connector should split multi-valued role attributes into multiple entries (CSV or multi-valued attributes) and map each to Redwood RBAC roles.

Temporary workaround provided to customer:
- In Okta, add an attribute transformation rule to emit two separate attributes (roles and roles_split) or make roles multi-valued instead of comma-separated; OR
- Create a console-level group mapping that maps the full comma string to a role (less desirable).

Investigation notes (internal):
- Initial triage: confirmed with customer SAML assertion. Verified that Okta was sending a single attribute with comma-delimited content (saml payload attached by customer to ticket).
- Connector behavior: sso-connector v2.4.1 reads attribute values and only treats repeated attributes as arrays; it does not parse delimiter-separated values.
- Recent change: a parsing refactor in sso-connector PR #395 (released in 2.4.0) removed implicit CSV splitting to avoid false positives; this resulted in stricter behavior in private deployments. Hosted Redwood previously applied a claim-normalizer layer which handled CSV. Private deployments rely solely on local connector behavior.
- Reproducible in staging: deployed sso-connector v2.4.1 in test private cluster and reproduced 403s using a crafted assertion.

Logs/highlights (sanitized):
- connector auth debug: "received attribute roles: \"admin,platform:deploy\""
- rbac match debug: "looking up role \"admin,platform:deploy\" -> not found"
- console audit: "user X attempted /deploy -> 403 -> missing role 'platform:deploy'"

Preliminary root cause hypothesis:
- Behavioral change from claim-normalizer removal combined with IdP emitting CSV in a single attribute leads to mismatch between expected multi-valued claims and actual attribute format.

Action items / next steps:
1) Short-term patch: add CSV-splitting logic back as a configurable toggle in sso-connector (PR in progress). Owner: Marco Delgado. ETA for patch: 2026-03-13.
2) Long-term: update private deployment docs and quickstart for Okta to include explicit guidance on multi-valued attributes vs. CSV and provide example transformation rules. Owner: Developer Experience.
3) Provide customer with a scripted Okta transformation or temporary group mapping steps. Owner: Support (Aisha).
4) Coordinate a minor private package release (v1.9.4) with patched connector and rollout notes. Owner: Release Engineering.

Customer communication summary:
- Informed customer of workaround (attribute transform) and that we are preparing a connector patch. Customer accepted workaround to unblock immediate operations and prefers a connector toggle in the next private release so they do not have to change IdP rules across many users.

Resolution notes (pending):
