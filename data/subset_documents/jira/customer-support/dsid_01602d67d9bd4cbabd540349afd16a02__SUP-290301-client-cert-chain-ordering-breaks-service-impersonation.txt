Client certificate chain ordering accepted by edge proxy but yields wrong subject -> service account impersonation fails in private VPC

Issue summary:
Customer reports that after rotating a service account client certificate in their private VPC, scheduled workers and admin impersonation calls started failing with 403s. The certificate upload process accepted the provided chain (end-entity cert + intermediate) but Redwood's identity proxy appears to map the request to the wrong service principal during mTLS subject extraction.

Impact:
- Multiple scheduled jobs (service-account impersonation) failing to call Redwood admin API in production (DataForge tenant).
- Customer-facing automation degraded: hourly ingestion jobs missing for ~6 hours.
- No token exchange logs for the expected principal; access denied responses returned.

Environment:
- Private deployment (VPC) in us-east; customer-managed edge proxy sits in front of Redwood private ingress.
- Identity proxy version: 1.14.3 (private image), OpenSSL 1.1.1k on proxy host.
- Customer rotated certificate via their internal CA and uploaded a concatenated certificate file (leaf followed by intermediate).

Steps to reproduce (provided by customer):
1) Upload client certificate bundle with end-entity cert first followed by intermediate cert to their on-prem SSO gateway (same bundle they use for mTLS).
2) Trigger admin impersonation endpoint (POST /v1/admin/impersonate) using mutual TLS client auth.
3) Observe 403 response from Redwood with no token issued to expected service account.

Observed behavior:
- Edge proxy TLS logs show a successful mTLS handshake but identity-proxy logs the client subject as "CN=old-service-account,OU=other,O=example" instead of the expected "CN=dataforge-svc-ingest,OU=svcaccounts,O=dataforge".
- Handshake excerpts include the peer certificates in transmitted order (leaf, intermediate).
- Identity proxy chooses the first certificate present in the chain for subject extraction when chain order is non-canonical.

Expected behavior:
- Identity proxy should canonicalize and validate the full chain, then extract the correct subject corresponding to the leaf certificate for impersonation mapping.

Relevant logs (redacted):
- identity-proxy: "mtls: peer certs count=2; using cert index=0 subject=CN=old-service-account,..."
- auth-proxy: "impersonation: mapping lookup failed for subject=CN=old-service-account -> mapping not found"
- customer-provided tcpdump/pcap shows TLS ClientHello and Certificate messages where certificates are concatenated leaf->intermediate.

Additional notes:
- Customer says their previous cert bundle uploads (with intermediate first) worked fine; their CA tooling appears to emit varying chain orders depending on packaging.
- Customer provided the exact PEM bundle and a PKI toolchain trace via secure share.

Initial hypothesis: rotation created a new subject that wasn't mapped. Reproduced failure without mapping issue — mapping existed but subject extracted differed.
Reproduction: local test with haproxy + identity-proxy shows OpenSSL hands certs to userland in the order transmitted by client; code assumed canonical order and used cert[0] as leaf.
Root cause: identity-proxy extracted the subject from the first certificate in the presented chain without canonicalizing/validating which cert is the end-entity. Some CA tooling emits end-entity first which flips the order and leads to extracting an intermediate or previous cert when multiple certs are concatenated incorrectly.
Risk assessment: High for private deployments where customers control the edge packaging process. Can cause broad impersonation failures for scheduled workers and automation that rely on client cert identity.
Short-term mitigation: instruct customers to provide a canonical bundle (leaf last / intermediate first) and restart edge process. Documented in runbook linked above.
Long-term fix: normalize chain order inside identity-proxy, validate chain, and prefer the verified leaf cert for subject extraction. PR created and targeted for next patch release (hotfix path available for severely impacted customers).
Related internal work: INT-4012 created to track rollout automation for private tenants and to add test vectors for different chain orders in CI.
Workaround applied: DataForge re-uploaded the certificate bundle with canonical order (intermediates first, leaf last) and restarted their edge proxy; scheduled jobs resumed. Engineering implemented a normalization and verification patch (PR 2045) to ensure identity-proxy derives the subject from the verified leaf even when clients present chains in arbitrary order. Patch queued for private hotfix release 1.14.4. Follow-up: schedule validation window with customer and add chain-order tests to CI.
