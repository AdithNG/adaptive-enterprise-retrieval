Private deployment: Admin API 403 on service-account impersonation after Azure Conditional Access device_compliant requirement

Issue summary:
Customers using our Private deployment with Azure AD as the OIDC provider report 403 responses when performing service-account impersonation via the Admin API. This started after the customer's tenant enabled a Conditional Access policy that requires device compliance for interactive and non-interactive tokens.

Impact:
- Admin API calls that rely on impersonation (service account -> user) return 403 for automated pipelines and SREs.
- Several scheduled jobs in FinTrail that rotate datasets and trigger model pushes are failing.
- No user-facing model serving impact observed yet, but operational tooling is broken.

Environment:
- Private deployment (customer-managed VPC) running Redwood platform v2025.11.2.
- IdP: Azure AD (tenant-specific CA policy).
- Affected endpoints: /admin/v1/impersonate, /admin/v1/users/*/roles

Observed behavior:
- Token exchange for impersonation (our service account exchanging a bound token) succeeds at Azure, but the id_token/access_token returned does not include the expected "device_compliant" claim. Admin API rejects with HTTP 403 and audit message: "device_compliance_required: claim missing or false".

Expected behavior:
- Service tokens used for server-to-server impersonation should be allowed if the token source is a verified service account and the Conditional Access policy explicitly targets interactive sessions only, or if customer has configured an exception for platform service accounts.

Additional notes:
- Customer confirms they did not change RBAC roles. The failure window matches the Conditional Access policy rollout (2026-03-10 09:00 UTC).
1) Customer sets Conditional Access policy in Azure AD requiring device compliance for both interactive and non-interactive flows.
2) Trigger service-account impersonation using Redwood Admin API from customer CI (service account key exchange flow).
3) Observe Admin API responds 403 with message referencing missing/invalid device compliance.
4) Reproduce confirmed by FinTrail on two separate service accounts and from two distinct subnets in their VPC.

Initial hypothesis: our token-introspection/claim-mapping pipeline is discarding a vendor-specific device compliance claim (xms_device_compliant / device_compliant) when tokens are exchanged for service accounts.
Triage actions taken:
- Confirmed timing correlation with customer's Conditional Access policy rollout.
- Verified introspection payloads from Azure - the original id_token for interactive users contains 'xms_cd' style claims but service account tokens omit them.
- Confirmed our idp-proxy currently treats device compliance claims as required only for interactive sessions according to documentation, but the customer's CA policy applies to non-interactive tokens as well.
- Observed rbac-cache TTL is 10m; customer saw repeated failures even after manual re-login which indicates tokens issued lacked the compliance claim at source.
Potential root causes:
- Azure CA policy is now applying to client_credentials/service principals in that tenant causing tokens to be issued without the compliance claim for service principals.
- Our claim-mapping config may not be including Azure's device compliance claim name variants (xms_example).
Next steps:
- Request sample introspection payloads from customer (done).
- Reproduce in internal staging with an Azure tenant and CA policy targeting non-interactive flows.
- Short-term workaround: advise customer to add an exclusion for Redwood service principal or to adjust CA policy to target only interactive users.
- Mid-term fix: add defensive claim-mappings for known Azure device compliance claim names and add a configurable bypass for verified service principal flows in the private idp-proxy config.
